# План цели content-factory-next-l9s

**Цель:** закрыть 16 заданных задач четырьмя последовательными волнами с наблюдаемым изменением и доказательством, которое ловит возврат дефекта, либо с записанным решением не менять.

**Подход:** одна активная стадия и четыре локальные ветки. Внутри волны независимые зоны записи выполняются параллельно, но волны не пересекаются: следующая начинается только после сфокусированных и полных проверок, независимого ревью, коммитов по задачам и локального слияния предыдущей в `main`.

**Не входит:** push, PR, публикация, deploy, работа с production-хостом или его данными, платные вызовы и закрытие задач владельца. `/home/me/code/content-factory` остаётся только для чтения.

**Спецификация:** `.codex/stages/content-factory-next-l9s/prompt.md`, `bd show content-factory-next-l9s` и карточки 16 задач.

## Решения до реализации

- `d08`: enterprise-путь подчиняется `CONTENT_FACTORY_REQUIRE_APPROVAL`; секретный JWT не является основанием обходить общий режим активации.
- `eh3`: предпочтительный результат — глобальный `whitelist: true`; агент обязан сначала проверить DTO и места, где контроллеры используют поля вне DTO. Если реальный маршрут зависит от лишнего поля и безопасная миграция не помещается в задачу, решение не включать должно быть доказано и записано.
- `c6k.15`: raw SQL и изменение существующих Temporal-контрактов запрещены. Если часы БД нельзя использовать через Prisma, приёмка требует поведенческого доказательства достаточности перепроверки владения, а не обхода запрета.

## Карта критериев

Все критерии и неизменяемые привязки находятся в `.codex/goals/content-factory-next-l9s/scope-criterion-snapshot.json` и в `stage-manifest.json`.

### Волна 1: права и вход

**Ветка:** `codex/2026-08-16-l9s-wave-1`

**Задачи:** `ao3`, `eh3`, `yhx`, `f36`, `d08`.

**Граница:** авторизация, вход, DTO-валидация и серверные запросы по пользовательскому URL. Каждое observable-изменение идёт по TDD; `eh3` включает аудит всех DTO-маршрутов. Проверка волны: сфокусированные тесты, backend typecheck, затем один общий набор цели и независимое senior-ревью.

### Волна 2: следы апстрима и SDK

**Ветка:** `codex/2026-08-16-l9s-wave-2`

**Задачи:** `4ug`, `ry5.7`, `ry5.8`, `4w5`, `527`.

**Граница:** механическая очистка цепочки поставки, SDK, локали и эксплуатационная документация. Для metadata/docs применяется `no-new-test`; brand-scan, сверка ключей локалей, submodule-проверка и build являются наблюдаемыми доказательствами. Решения владельца переносятся только комментарием в `woy`.

### Волна 3: дизайн-долг

**Ветка:** `codex/2026-08-16-l9s-wave-3`

**Порядок:** `rcg.2` строго первой; затем `rcg.1`, `rcg.3`, `rcg.4`.

**Граница:** сначала guard для геометрии и существующий allowlist, затем общие layout/control-примитивы и их реальные потребители. Перед UI-реализацией используются Impeccable и Lazyweb-маршрутизация согласно контракту репозитория. Проверка включает мутацию нового off-rhythm значения, четыре design/foundation набора и frontend build.

### Волна 4: надёжность и данные

**Ветка:** `codex/2026-08-16-l9s-wave-4`

**Задачи:** `c6k.15`, `7g0`.

**Граница:** конкурентность Telegram и локально проверяемый backup/restore. Изменение Prisma-схемы допустимо только через Prisma без raw SQL и с поведенческим тестом рестарта. Механизм резервирования проверяется на локальной базе; применение на хосте остаётся отдельным действием владельца.

## Приёмка

- После каждой волны: сфокусированные проверки задачи, `pnpm run build`, `pnpm test`, `node scripts/branding/brand-scan.cjs`, `git diff --check`, `scripts/orchestration/run_process_verification.sh`, запись чисел и независимое ревью.
- Коммиты — по одной задаче, затем локальное слияние волны в `main`.
- В конце: документационное и Graphify-решения, обновлённый handoff, стадийные артефакты, финальная сверка открытых Beads после `bd dolt pull`.
