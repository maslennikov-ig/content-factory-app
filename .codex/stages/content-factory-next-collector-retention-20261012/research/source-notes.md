# GlitchTip retention feasibility (read-only)

Checked 2026-10-12 for Beads task `content-factory-next-0qgn.5.1`. Scope: error events and files in the shared collector; no runtime, database, configuration, Beads, or source changes were made.

## Decision

**GlitchTip 6.0.5 has no native per-project event or file retention override.** Its built-in retention is global. Keep the shared collector at 90 days while other projects depend on it. If Content Factory must have 30-day deletion without changing those projects, the simplest safe operating boundary is a dedicated collector and storage with 30-day instance settings. A project-scoped janitor would be new destructive code, not a supported setting or command.

## Confirmed v6.0.5 behavior

- The `maintain_partitions` management command takes no project argument. It applies `GLITCHTIP_MAX_EVENT_LIFE_DAYS` to the `issue_events_issueevent` daily partitions and uses the same global value for weekly `IssueAggregate`, `IssueTag`, and project-stat partitions ([command](https://gitlab.com/glitchtip/glitchtip-backend/-/blob/v6.0.5/glitchtip/management/commands/maintain_partitions.py#L11)).
- Event `id` is server-generated UUIDv7 from `processing_event.received`; `IssueEvent.timestamp` comes from the client payload ([event model](https://gitlab.com/glitchtip/glitchtip-backend/-/blob/v6.0.5/apps/issue_events/models.py#L190), [ingest write](https://gitlab.com/glitchtip/glitchtip-backend/-/blob/v6.0.5/apps/event_ingest/process_event.py#L868)). Therefore native event age is **time accepted by GlitchTip**, not client event time. The partition manager drops entire date partitions using the global age and `DROP TABLE ... CASCADE` ([partition manager](https://gitlab.com/glitchtip/glitchtip-backend/-/blob/v6.0.5/glitchtip/partition_manager.py#L308), [age cutoff](https://gitlab.com/glitchtip/glitchtip-backend/-/blob/v6.0.5/glitchtip/partition_manager.py#L348)). Event partitions are range-partitioned by UUIDv7 `id` and hash-subpartitioned by `organization_id`; dropping one date parent removes every organization/project row in it.
- A safe project join exists in the data model: `IssueEvent -> Issue -> Project`; each Issue belongs to one Project. `IssueAggregate` and `IssueTag` also reference that Issue, while project-hour statistics have their own `project` FK ([issue models](https://gitlab.com/glitchtip/glitchtip-backend/-/blob/v6.0.5/apps/issue_events/models.py#L40), [project statistic model](https://gitlab.com/glitchtip/glitchtip-backend/-/blob/v6.0.5/apps/projects/models.py#L181)). These relationships can scope a custom ORM cleanup. No built-in retention method uses them.
- The stock cleanup keeps grouped Issue rows until their event, aggregate, and tag rows are all gone; then it deletes the issue's hashes, comments, user reports, and issue row in batches ([cleanup](https://gitlab.com/glitchtip/glitchtip-backend/-/blob/v6.0.5/apps/issue_events/maintenance.py#L11)). Issue `count`, `last_seen`, and search vector are denormalized summaries updated at ingest. A custom partial event deletion must explicitly decide the lifetime of corresponding aggregate/tag/project-stat rows and whether those Issue summaries remain 90 days. Deleting an Issue or invoking project deletion is broader: project deletion queues a force-delete of all project events and related issue data ([Project.delete/force_delete](https://gitlab.com/glitchtip/glitchtip-backend/-/blob/v6.0.5/apps/projects/models.py#L68), [task](https://gitlab.com/glitchtip/glitchtip-backend/-/blob/v6.0.5/apps/projects/tasks.py#L7)).
- File retention is also global and has no dry-run argument. `cleanup_old_files()` chooses blobs by global `FileBlob.created`, removes the physical blob, then deletes its database row ([file cleanup](https://gitlab.com/glitchtip/glitchtip-backend/-/blob/v6.0.5/apps/files/tasks.py#L20)). A FileBlob is checksum-deduplicated across multiple File rows; FileBlob has no project FK, and deleting it cascades to its File rows ([models](https://gitlab.com/glitchtip/glitchtip-backend/-/blob/v6.0.5/apps/files/models.py#L25)). DIF metadata has a project FK to File, but release/debug-symbol references may be organization- or release-scoped ([DIF model](https://gitlab.com/glitchtip/glitchtip-backend/-/blob/v6.0.5/apps/difs/models.py#L5), [DebugSymbolBundle model](https://gitlab.com/glitchtip/glitchtip-backend/-/blob/v6.0.5/apps/sourcecode/models.py#L6)). There is no safe way to infer exclusive CF ownership from a FileBlob row; a CF-only cleaner would have to preserve any blob still referenced by another project or release.
- `perform_maintenance` invokes the global partition and file cleanup functions without filters or dry-run ([maintenance task](https://gitlab.com/glitchtip/glitchtip-backend/-/blob/v6.0.5/glitchtip/tasks.py#L11)). No retention-specific management command with project arguments was found in the v6.0.5 source.

## Recommendation and bounded unknowns

Leave shared 90-day settings unchanged. For an actual 30-day CF policy, prefer a dedicated collector/store so stock global cleanup becomes CF-only. If the shared instance must remain, treat a project-scoped janitor as a separate implementation stage: first produce a read-only candidate inventory; filter events through `issue__project_id` using UUIDv7 receipt age; scope matching IssueAggregate/IssueTag and project-stat rows consistently; and delete a FileBlob only after checking all File, DIF, release, and foreign-project references. This stage must choose whether 30 days applies to client timestamp or receive time. Stock GlitchTip uses receive time; root reports the current 39/100 aged events under both timestamp and UUIDv7 checks, so the current snapshot does not decide that policy question.

The researcher did not inspect event payloads or host/database rows. Whether any CF blob is referenced by another project, and the intended retention of aggregates/tags and Issue summaries, remain UNKNOWN pending metadata-only inventory and product policy. No tests or local acceptance were run; root owns final acceptance.
