### PRV-01 — OAuth token fan-out lacks organization isolation

- **Evidence:** `libraries/nestjs-libraries/src/database/prisma/integrations/integration.repository.ts:439–464`: the primary upsert is tenant-bound, but its subsequent `updateMany` only uses `id != upsert.id` and `rootInternalId == rootId`. Both `organizationId` and provider cohort are absent. The row's access/refresh token and refresh-needed flag are overwritten.
- **Reachable caller:** `apps/backend/src/api/routes/no.auth.integrations.controller.ts:260–288` passes `!!integrationProvider.oneTimeToken`; `linkedin.provider.ts:31` enables this flag, and `linkedin.page.provider.ts:19–25` inherits it. `RefreshIntegrationService.refresh` also reaches the same upsert (`refresh.integration.service.ts:30–42`). Two organizations may connect the same external account; their distinct database rows then share the external root ID.
- **Impact:** connecting or refreshing organization A changes organization B's publishing credential/state. Even a same-organization unrelated provider with a colliding root ID is included by this query. This is an isolation/data-integrity defect, independent of whether the token's platform privileges happen to overlap.
- **Pure evidence:** executing the current repository class with an in-memory Prisma adapter, two LinkedIn rows in `org-a` and `org-b`, and one refresh for A produced:

```json
{"query":{"id":{"not":"ia"},"rootInternalId":"same-external-user"},"otherTenantToken":"fresh-a","otherTenantRefreshToken":"fresh-ra"}
```

- **Smallest fix / expected value:** constrain fan-out to the current organization and the explicitly supported credential-sharing provider family. Preserve intentional sharing between a LinkedIn account and its linked pages inside that organization.
- **Minimum acceptance:** a two-organization test with the same root external ID must prove B's token, refresh token, expiry and refresh-needed flag unchanged; same-tenant linked pages must still receive the permitted refresh. Include an unrelated provider with the same root string.
- **Tradeoff:** blindly requiring exact `providerIdentifier` would break intended account/page sharing; establish the allowed cohort rather than removing fan-out wholesale. **Confidence: high.**

### PRV-02 — Post success is coupled to a fallible auxiliary workflow

- **Evidence:** `apps/orchestrator/src/activities/post.activity.ts:247–284` awaits `provider.post`, then awaits `workflow.start('streakWorkflow')`, then returns the provider result. An error in the second call loses that result. V105 `post.workflow.v1.0.5.ts:19–27` retries this activity three times; the post receipt is persisted only afterwards, at `:195–200`.
- **Reachable trigger:** normal queued publication via `PostsService.startWorkflow` (`posts.service.ts:827–866`); provider accepts the post, then the streak start RPC fails or the process dies before the activity result becomes durable.
- **Impact:** external duplicates and an ERROR/QUEUE row whose actual publication result was lost. The helper is a reminder, but its failure retries the external write. Generic network/worker failure after provider acceptance remains a related uncertainty boundary.
- **Pure evidence:** the actual activity class, fake provider and failing streak client, called for the configured three attempts, reported `activityAttempts=3`, `externalPublishes=3`, `streakStarts=3`.
- **Smallest fix / expected value:** introduce a versioned posting workflow/activity chain that durably records the provider result before starting auxiliary work, with idempotency/reconciliation for uncertain provider outcomes. A streak error must never reissue an already confirmed publish. Keep historical workflow/activity contracts intact.
- **Minimum acceptance:** confirmed provider result + failed streak start yields one provider write, a persisted provider ID and a separately visible auxiliary failure. Add a restart/uncertain-response boundary case; a fake can prove the local control flow, not provider-side exactly-once delivery.
- **Tradeoff:** one more durable step/receipt; provider APIs without idempotency require an explicit uncertain state rather than a blind retry. **Confidence: high.**

### PRV-03 — Extension refresh can resurrect a deleted integration

- **Evidence:** `apps/backend/src/api/routes/no.auth.integrations.controller.ts:393–459` verifies the extension JWT and checks only that the integration exists and its external ID matches. `IntegrationRepository.getIntegrationById` (`integration.repository.ts:518–524`) returns soft-deleted rows. The refresh then calls `createOrUpdateIntegration`, whose update sets `deletedAt: null` (`:434`) and `refreshNeeded: false` (`:435`). The token is signed without expiry/revocation state (`no.auth.integrations.controller.ts:343–349`, `libraries/helpers/src/auth/auth.service.ts:62–66`).
- **Reachable trigger:** remove a Skool channel from another browser/device, or the original extension misses the best-effort `REMOVE_REFRESH_TOKEN` message (`apps/frontend/src/components/launches/menu/menu.tsx:297–311`); its later valid refresh request restores the deleted row. Direct authorized-token POST is independently reachable even while the normal extension CORS path is broken (PRV-10).
- **Impact:** deletion does not revoke this credential's mutation authority; a removed channel reappears with usable credentials without a new connect action.
- **Pure evidence:** the current extracted controller method, a valid synthetic token payload, a row with non-null `deletedAt`, and matching fake provider authentication returned `success: true` and invoked the upsert. The current upsert explicitly clears `deletedAt`.
- **Smallest fix / expected value:** reject deleted/disabled or otherwise revoked integrations before provider authentication; bind the token to the current connection generation so deletion/reconnection invalidates old tokens. A refresh should update an existing live row rather than use a reconnecting upsert.
- **Minimum acceptance:** retained token after deletion returns 404/409 without provider authentication or database update; after reconnect, the previous connection generation is refused while the new one works. Test a missing extension cleanup message.
- **Tradeoff:** token reissuance/migration for existing installations; do not change the general legacy JWT helper's consumers to solve one endpoint. **Confidence: high.**

### PRV-04 — Bold backfill's write does not preserve its manual-edit check

- **Evidence:** `apps/commands/src/tasks/rerender.adaptation.bold.ts:175–188` checks a snapshot's content equals the old machine render, but the update only checks ID, organization, DRAFT and not-deleted. It does not compare the content or derivation version read. The citation backfill already demonstrates a conditional content/body update pattern (`strip.adaptation.citation.labels.ts:160–176`).
- **Reachable trigger:** `adaptations:rerender-bold --apply` runs while a person edits one selected draft after `findMany` but before `updateMany`.
- **Impact:** their new text is replaced by the old body's render. The operator command's documented promise to leave manually edited drafts untouched does not hold under concurrency.
- **Pure evidence:** current command class with a fake Prisma adapter: snapshot content `**Machine**`; then stored content `User edit after snapshot`; update predicate omitted content; final stored content became `<b>Machine</b>`.
- **Smallest fix / expected value:** compare the exact previously read post content in the write; also fence the derivation body/version if rendering relies on it. Count a moved row as skipped.
- **Minimum acceptance:** edit post content and separately change derivation body between read and apply; both must remain untouched. Normal untouched row still renders once. Existing tests (`tests/adaptation-bold-backfill.test.cjs:83–93,158–175`) cover an edit present before reading, not an edit between read/write.
- **Tradeoff:** concurrent edits skip some rows rather than forcing the backfill through; expected safe behavior. **Confidence: high.**

### PRV-05 — Cached automation bypasses current disable state

- **Evidence:** V105 stores the plug list before its sleeps (`post.workflow.v1.0.5.ts:278–323`) and later calls `processPlug` (`:365–368`). `IntegrationRepository.getPlug` (`integration.repository.ts:262–270`) loads any row by ID, including inactive plugs and disabled/deleted channels. `IntegrationService.processPlugs` (`integration.service.ts:871–888`) immediately calls its stored provider method, with no activation/channel-state or current allowed-metadata check. X's `autoRepostPost`/`autoPlugPost` flags hide the plugs from new lists (`x.provider.ts:164–167,245–248`) but their execution bodies still call analytics/write APIs (`:199–204,287–297`).
- **Reachable trigger:** after an action was put in a workflow's delayed list, turn off the plug/channel or deploy `DISABLE_X_ANALYTICS=1`; the existing workflow still wakes and invokes the old action. `changePlugActivation` only updates the row; it does not erase an existing workflow's list.
- **Impact:** retweet/reply/analytics work after explicit disablement. Disabling UI discovery protects future lists but does not protect already scheduled consumers.
- **Pure evidence:** current extracted `processPlugs`, plug `activated=false`, channel `disabled=true/deletedAt!=null`, and no allowed metadata still made one fake provider call.
- **Smallest fix / expected value:** gate at execution time on plug activation, live channel state and currently allowed plug metadata; skip a now-disabled item without invoking the provider. Provider-specific kill switches should also be checked inside that provider's operation.
- **Minimum acceptance:** schedule an action, then turn off plug and channel in separate cases; waking it makes zero provider calls. A restart with `DISABLE_X_ANALYTICS=1` must refuse an action already in history. Keep Temporal argument signatures intact/version successors where required.
- **Tradeoff:** a cancelled automation step finishes as skipped; no need to mutate historical workflow lists or delete rows. **Confidence: high.**

### PRV-06 — Webhook looks up a provider ID as an internal database ID

- **Evidence:** V105 passes `postsResults[0].postId` to `sendWebhooks` (`post.workflow.v1.0.5.ts:272–275`). By interface this is the provider's post ID (`social.integrations.interface.ts:117–123`). `PostActivity.sendWebhooks` (`post.activity.ts:345`) passes it to `getPostByForWebhookId`, whose Prisma query is `where: { id: postId }` (`posts.repository.ts:1746–1751`).
- **Reachable trigger:** any ordinary successful post with an external ID different from the internal Post.id, with an enabled publishing webhook.
- **Impact:** webhook delivery contains `[]` instead of the post and its release URL/state. A successful HTTP response cannot establish event content correctness.
- **Pure evidence:** extracted current activity with local row `local-post` and argument `remote-provider-id` sent JSON `[]` to the fake webhook.
- **Smallest fix / expected value:** version the current posting chain to use internal Post.id for the event lookup and retain external post ID as an explicit separate field. Keep the old exported workflow/activity contract available.
- **Minimum acceptance:** internal and provider IDs deliberately differ; payload includes the intended organization's post and provider release URL. Check response status and visible delivery failure as part of the event-delivery contract.
- **Tradeoff:** versioned event/consumer migration; do not silently swap an argument's meaning for already-running histories. **Confidence: high.**

### PRV-07 — Nostr's reported identity is unrelated to the accepted event

- **Evidence:** `nostr.provider.ts:99–129` subscribes to *any* kind-1 event by the author, publishes the new event, then takes the subscription's first event ID. There is no ID predicate. All relay errors are swallowed. `:188–195` returns `status: 'completed'` even if the resulting ID is empty. The provider is registered (`integration.manager.ts:64`).
- **Reachable trigger:** author has an older event on a relay; or every relay refuses/connect fails/EOSE yields no event. Both main posts and comments use this publisher.
- **Impact:** the post links to an unrelated old publication or an empty URL, while the common workflow marks it published. A relay failure can be represented as completed work with no provider receipt.
- **Pure evidence:** actual provider class with fake relays acknowledging `new-event` but emitting `old-event` returned `postId='old-event', status='completed'`. With all five relays throwing, it returned `postId='', releaseURL='https://primal.net/e/', status='completed'`.
- **Smallest fix / expected value:** use the signed new event's ID only after at least one matching relay publish acknowledgement; surface all-relays failure explicitly; close connections on failed paths too. Retry the same signed event when permitted rather than generating a distinct timestamp/event blindly.
- **Minimum acceptance:** old author events cannot replace the new ID; all failures/empty EOSE cannot return completed; exact acknowledged new event returns its ID; comments retain parent linkage. No real relay needed for local proof.
- **Tradeoff:** stricter acknowledgement may reveal existing failed posts; historical provider results require reconciliation, not automatic republication. **Confidence: high.**

### PRV-08 — Sorted delay offsets are accumulated rather than respected

- **Evidence:** global actions get offsets `current.delay * i` (`post.workflow.v1.0.5.ts:285–291`), then the sorted list sleeps each full `todo.delay` (`:311–323`). An elapsed/previous deadline is not subtracted. Repeat-post delay is another offset in the same list (`:299–309,416–435`).
- **Reachable trigger:** a provider plug with `totalRuns>1` (for example X's 6-hour, three-run plug) or any plug combined with a repeating post.
- **Impact:** 6/12/18-hour plug deadlines run at 6/18/36 hours. A 24-hour repeat after those entries can run at 60 hours. One action's wait moves later unrelated actions as well.
- **Pure evidence:** current V105 under an in-memory virtual clock with nominal plug offsets `[1000,2000,3000]` ran at `[1000,3000,6000]` milliseconds; requested sleeps were `[1000,2000,3000]`.
- **Smallest fix / expected value:** create a versioned workflow that stores an absolute deadline/base and waits only until each deadline; account for activity processing time. Define repeat interval relative to actual publication rather than time spent waiting for the initial scheduled post.
- **Minimum acceptance:** virtual-clock multiple plug deadlines plus a repeat retain their declared times; nonzero provider processing time does not add drift; no negative sleep; current V101–V105 replay paths remain available.
- **Tradeoff:** old executions retain their original timing unless deliberately migrated; do not alter V105's command sequence in place. **Confidence: high.**

### PRV-09 — Refresh-all aborts on the first unrefreshable channel

That service marks the first failed integration as refresh-needed, then `return`s from the complete loop (`integration.service.ts:578–597`). - **Smallest fix / expected value:** process failures per integration, continue the bounded batch, report succeeded/failed/skipped counts and a useful command exit status. Respect manual-reconnect/non-renewable providers rather than treating dummy refresh returns as valid credentials.

- **Tradeoff:** partial-success semantics must be explicit; never retry an uncertain rotated refresh credential blindly. **Confidence: high.**

### PRV-10 — Extension production package lacks backend request permission

- **Evidence:** production `apps/extension/package.json:7` uses `vite.config.ts` then copies the static manifest. Its `manifest.json:17–19` grants only `*.skool.com` host access. The cookie refresh service worker posts JSON to `${entry.backendUrl}/integrations/extension-refresh` (`background.ts:95–111`), passed by the actual frontend (`continue.integration.tsx:167–184`). `externally_connectable.matches` permits receiving messages from Factory/localhost, but is not remote host permission. Backend CORS allows only FRONTEND_URL/MAIN_URL/local inspector (`apps/backend/src/cors.options.ts:44–50`), not the extension origin. The alternate `vite.config.base.ts` host calculation is not used by the production build; the dev manifest merge also replaces its host list with Skool-only permissions.
- **Reachable trigger:** normal packaged extension successfully extracts and stores cookies, then its daily alarm tries background renewal against Factory or a self-hosted backend.
- **Impact:** the background request is rejected by browser CORS without the backend permission; errors are swallowed and response status is never checked, so the UI may appear connected until cookies expire. Ordinary “extension installed”/PING proof would miss this path.
- **External contract:** Chrome documents that cross-origin extension requests require matching host permissions to bypass the ordinary origin restrictions: [Chrome extension network requests](https://developer.chrome.com/docs/extensions/develop/concepts/network-requests).
- **Smallest fix / expected value:** package a valid, explicit allowed backend host permission (or request an optional host grant), validate stored backendUrl against the connected deployment, and show/refuse failed renewals rather than dropping them silently. `externally_connectable` and cookie-source permissions have separate purposes.
- **Minimum acceptance:** inspect the exact packaged manifest, then an unpacked built extension performs a renewal to a disposable local backend with the production-style CORS contract; denied host grant/HTTP 401 is visible. This review did not build/install/open the extension.
- **Tradeoff:** granting a backend host increases permission scope; use exact deployment hosts rather than a blanket all-URLs grant. **Confidence: high for source/contract mismatch; browser runtime occurrence unverified.**

### PRV-11 — Forever-running histories are not bounded consistently

- **Evidence:** `autopost-draft-v2.workflow.ts:20–33`, `autopost.workflow.ts:14–29` and `missing.post.workflow.ts:13–19` loop indefinitely without `continueAsNew`. Active callers exist in `autopost.service.ts:224–264` and `temporal/infinite.workflow.register.ts:8–17`. `send.email.workflow.v2.ts:115,134–135` advances the rotation counter only for successful sends; arbitrarily many dropped failed sends never rotate. In contrast, content-lead checks bound 100 attempts (`content-lead-check.workflow.ts:27–55`) and digest already rotates. Its comment that AutoPost V2 itself rotates is contradicted by current code (`content-lead-check.workflow.ts:21–25`).
- **Impact:** every timer/activity/failure adds history to the same run; long-lived subscriptions/recovery and failure-heavy mail eventually hit configured server limits, with increasing replay cost before then. Exact current history sizes, dynamic server limits and time-to-limit are UNKNOWN.
- **External contract:** [Temporal Continue-as-New](https://github.com/temporalio/documentation/blob/main/docs/develop/typescript/workflows/continue-as-new.mdx) is the documented history-reset boundary. This finding does not assume a specific current server limit or claim a measured incident.
- **Smallest fix / expected value:** add successor periodic workflow versions with bounded iteration/history rotation and preserve input/queue state; count processed attempts, not only successful deliveries. Migrate starts deliberately, preserve historical exports and inspect idle/running legacy consumers before any cleanup.
- **Minimum acceptance:** a virtual clock/counter reaches the bound and invokes exactly one continuation with preserved state; a failure-heavy mail stream still rotates; queued work/signals at rotation are neither lost nor duplicated. Root owns one final set and any real history/restart proof.
- **Tradeoff:** versioned migration and signal handoff coverage. Changing loops in already-recorded workflows is not the proposed fix. **Confidence: high for unbounded source growth; current production proximity to limits unknown.**
