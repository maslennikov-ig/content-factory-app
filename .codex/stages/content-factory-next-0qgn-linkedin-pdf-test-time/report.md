# Test-only PDF creation-date repair

Root's still-running exact d67 release check found the new PDF equivalence test comparing `(D:20261002051849Z)` with `(D:20261002051850Z)` in indirect object 16. The previous normalizer only matched an inline `/CreationDate (D:...)`. Installed PDFKit 0.15.2 serializes every info value into a referenced object in `PDFDocument.end()`; its Date serialization and file ID use the creation timestamp. The discrepancy was a test defect; production conversion did not change.

The repaired comparison follows the final trailer's Info reference, reads its CreationDate reference, and normalizes only that referenced UTC value. It also normalizes only the two file IDs in the actual final trailer. Replacement values have the same lengths. Object IDs, dictionary references, whitespace, every other object/stream/image/page dimension, the complete xref bytes, trailer structure and EOF remain in the comparison. Unexpected PDFKit metadata shape fails explicitly. This helper is for these generated PDFKit fixtures, not a general PDF parser.

An actual PDFKit fixture with explicit creation seconds `2001-01-01T00:00:00Z` and `00:00:01Z` reproduced RED with the old normalizer: one failed test, sixteen filtered. Fixed explicit moments do not depend on today and do not alter global Date/timers. After the fix, equal content across those two seconds compares equal. Separate countercases change real JPEG pixels, MediaBox dimensions or an unrelated ModDate and still compare different. The positive test also checks unchanged total length and exact xref bytes. The original direct installed image-to-pdf/sharp two-page equivalence and all thirteen original import/stream/error regressions remain active.
