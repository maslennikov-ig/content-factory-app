# Social factory V1

A owns this directory, persistence, shared schema, module/controller wiring and the native capability registry. B owns profiles/discovery/editorial, C owns video, D owns measurement/learning/attribution. The shared contract is additive; request changes through the manager rather than forking wire shapes.

`social-factory.v1.ts` is the versioned boundary. Existing content piece/derivation, integration, media and post IDs remain authoritative; campaign items reference them. All API identity comes from the authenticated server context. IDs never substitute tenant scope.

## Persistence and authority

Inject `SocialFactoryRepository` from `../social-factory.repository` using the `SocialFactoryStoreV1` methods: `read<T>(org,kind,id)`, `list<T>(org,kind,limit?)`, `put<T>({organizationId,kind,id,payload,expectedRevision})`, `remove(org,kind,id,expectedRevision)`. A supplies this Prisma-backed implementation and registers downstream providers. Revision 0 creates; subsequent writes compare the stored revision. Missing/deleted reads return null. Conflicts return `SOCIAL_FACTORY_CONFLICT`; tenant reads cannot see another organization's ID. Each downstream service owns validating payloads and referenced IDs.

Domain DTOs may extend shared interfaces. Register resource kind additions with A; do not add another data store. `observation`, `decision`, `exchange`, and `action` payloads are immutable journals: only revision 0 creates are allowed. Deletion/invalidation is explicit and recorded; a hidden/deleted record cannot be recreated by a stale revision-0 retry.

Default campaign mode is `prepare_approve`. Counts are explicitly allocated by channel and format; story count means frames, carousel count means publications, with slide count retained. Approval binds a content revision and digest. Provider receipt, uncertain submission, local readiness and external publication are distinct. Grants never supply missing business facts, source rights, provider consent or additional funding. Replacing/removing the campaign grant invalidates affected queued agent actions and later thread parts. Separately confirmed human scheduling retains its explicit authority; direct grant revocation and campaign stop still block pending sends.

`transact(work)` supplies the same store bound to a serializable Prisma transaction (bounded retry on P2034). Use it for multi-record invariants such as campaign allocation, grant revocation/action admission and approval transition. No external I/O inside the callback: it can replay after a database conflict. `put` accepts optional `parentId`; `list(org,kind,limit?,parentId?)` can list one campaign's resources without scanning unrelated campaigns.

## Production and native delivery

The chat/controller entrypoints use [production.service.ts](../production.service.ts), [native-material.service.ts](../editorial/native-material.service.ts) and [publishing.service.ts](../publishing/publishing.service.ts). `campaign.plan_materials` resolves distinct assignments and per-item Telegram length choices before generation; `campaign.prepare` consumes those selections. Autopilot editorial answers come from the configured advanced product model, with persisted provenance and current grant checks. The [decision service](../autonomy/editorial-decision.service.ts) captures its output before domain persistence, allowing a known result to finish without another paid call. It cannot fill missing business facts or self-authorize rights/budget.

Autopilot preparation does not imply delivery permission. Before automatic approval, the current grant must allow both `schedule` and `publish` for the item and planned posting window. Otherwise the operation records `deliveryRequiresApproval` with `AUTONOMY_DELIVERY_APPROVAL_REQUIRED`, leaves the item `ready` without approval, and makes no delivery attempt. A later default-grant change does not clear that approval requirement.

Campaign generation checkpoints are owned by tenant/item/content revision, independently of transport request IDs. Keep the original request identity through plan/prepare/retry. Known outputs resume artwork/native persistence; unknown paid results and unresolved partial assets remain blocked. Current profile/brand/findings, source admissions, item revision and campaign authority are rechecked before applying output. Native drafts reference the existing piece/derivation/media records; they are not a separate editor or publication queue.

`campaign.edit` changes only public text/caption or one thread part and revokes earlier approval. Video caption edits use the production owner's CAS/lease and a deterministic native-save receipt; preserve script/scenes/assets and unfinished-video blockers; reject unresolved/launchable bound video work; and persist a human override across later reinspection. Explicit `campaign.reinspect` requires a known output checkpoint and `expectedContentRevision`; it normalizes/rechecks that output without a model call, reuses only validated unchanged Story/carousel assets or an unbound video cover, and may create first artwork from saved frames. Its saved revision always requires a fresh approval, including under autopilot. It never publishes, replaces a lost model response or silently retries unresolved artwork.

Explicit `campaign.revise` starts a new paid visual/text production revision for only the selected item. Its author request ID, target, expected content revision and instruction are persisted atomically before ordinary preparation. It preserves old immutable results/assets and siblings; ordinary `campaign.prepare` never creates another paid revision merely because a transport request ID or instruction changed. Inflight/unknown output remains locked. The response's `resumeInput` is the exact continuation contract: when Telegram needs a new length choice, pass it to `campaign.prepare`, changing only the selected item's `lengthChoiceId`/`lengthGuidance` and retaining its saved request ID/instruction. Calling `campaign.revise` again with another ID creates a different edit intent, not a length answer. `campaign.edit` remains caption/text-only; selective video-scene changes use the existing immutable video production revision.

Video preparation remains `needs_video` until an existing production revision completes. Bind/create, preflight, confirm launch and finalize use the existing video job engine. Selective scene changes use a new manifest/parent revision; storage retry imports the existing result. Final inspection requires actual owned metadata/caption evidence, with incomplete output retained as `needs_revision`. Final videos send one final video attachment; covers and subtitle files remain inspectable material assets, with supported YouTube cover metadata mapped to its native thumbnail setting.

Campaign-bound posts start `postWorkflowV109`; ordinary posts retain V108. Recovery uses the new `missingPostWorkflowV110` to select the appropriate workflow. Prior Temporal workflow/activity contracts remain unchanged. V109 reads the authoritative native payload and validates the actual prepared outbound text/settings/media. `claimNativePublication` commits current campaign admission and the native V106 receipt-journal claim in one transaction, so a known pre-send claim failure rolls both back. The journal remains the receipt authority: confirmed retries project the same receipt, pending/unknown sends never start a fresh write. Every thread part has its own binding/receipt and rechecks authority before its send; a confirmed root alone does not complete a thread.

## Source lifecycle

Lineage has explicit namespaces: `sourceRef(sourceId)` = `source:<canonical Source ID>` and `resourceRef(kind,id)` = `resource:<kind>:<id>`. Evidence identity is separate (`Evidence.id` vs `Evidence.sourceId`). Domain writers pass these typed refs as `sourceIds`; never raw ambiguous IDs. Source revoke calls `invalidateBySource(org, canonicalSourceId)`, which traverses typed dependent refs. Explicit source withdrawal and true permission/retention expiry redact derived text in records, native pieces/derivations/posts, and queue proven generated assets for physical storage deletion. Owner-authored campaign allocation/settings survive; publication receipts remain distinct from removed source content. Originals explicitly recorded in `visualSourceMediaIds` are retained.

Freshness is separate from storage rights. `source.freshUntil`, snapshot HTTP `expiresAt`, discovery caches, profile snapshots and planning findings can become stale without deleting prepared or published history. `purgeExpired` clears stale planning payloads but stops that expiry cascade before ready materials; expired observations can clear findings without erasing content already planned from them. New planning/admission must still resolve current permitted fresh context. Only actual snapshot `retentionUntil` and source-purpose permission deadlines become inferred native-material storage limits. Exact same-scope live permission extensions renew those inferred limits using every original source snapshot/permission, preserving earlier constraints of other sources; the old permission admission revision remains stale.

`readSourcePermissionState` returns absent/present/unknown including expired or deleted tombstones. Never convert a revoked or unreadable grant into an absent baseline permission. Ordinary confirmed first-party/web sources can use the canonical authority baseline; Telegram reuse and licensed exports need the appropriate persisted scope and provenance. `transactSourcePermission` and `assertSourceAdmissions` serialize source changes with native writes. `assertBrandProfileVersion` locks the actual native brand/profile version before derived persistence; selecting a different default only makes prior context stale.

These are implementation contracts. Runtime, provider-account, content-quality and release acceptance are separate evidence; the [chat/editor guide](../../../../../../docs/operations/agent-chat-editor-guide.md) describes the user journey.
