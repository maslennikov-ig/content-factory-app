# Подготовка входа через Telegram: ручные шаги владельца

**Статус:** `runbook`
**Проверено:** 2026-08-16 на коммите `f7fc31d1` плюс правки аудита

Код входа через Telegram уже в `main`. Он **не заработает сам по себе**: три вещи
может сделать только владелец — выдать учётные данные у BotFather, применить
схему к базе и положить значения в окружение. Ниже — точный порядок и способ
убедиться, что шаг удался.

Ничего из перечисленного нельзя выполнить за вас: это внешний сервис, реальная
база и секреты.

## Что уже сделано за вас

- Провайдер, кнопка, тексты во всех шестнадцати локалях и тесты — в `main`.
- Значение `TELEGRAM` добавлено в enum `Provider` **в файле схемы**.
- Кнопка скрыта, пока не заданы обе переменные, поэтому текущий продакшен
  ничего не показывает и ничего не ломает.

## Шаг 1. Учётные данные у BotFather

1. Откройте [@BotFather](https://t.me/BotFather) и выберите своего бота
   (или создайте новым `/newbot`). Это тот же бот, что публикует в каналы, —
   отдельный заводить не нужно.
2. Мини-приложение BotFather → бот → **Login Widget**.
3. Скопируйте **client id** и **client secret**. Это не `TELEGRAM_TOKEN`:
   токен публикации не подходит для входа и наоборот.
4. В **Allowed URLs** внесите точный адрес возврата:

   ```
   <ваш FRONTEND_URL>/auth?provider=TELEGRAM
   ```

   Для развёрнутого инстанса это ровно:

   ```
   https://factory.aidevteam.ru/auth?provider=TELEGRAM
   ```

   Адрес сверяется посимвольно: лишний слэш в конце, `http` вместо `https` или
   другой поддомен — и Telegram откажет.

   **Строка ровно одна, второй быть не должно.** Через неё же идёт привязка
   Telegram из «Настройки → Способы входа»: продукт отправляет в Telegram
   всегда этот адрес, а дальше две стороны делают две разные вещи. Куда
   вернуть человека — в настройки или внутрь после входа — решает браузер:
   вкладка, начавшая привязку, оставляет заметку в `sessionStorage`
   (`content-factory:identity-link-intent`, пять минут), страница `/auth` её
   читает и сама уводит на `/settings`; в Redis этой заметки нет, не ищите её
   там. Чем нельзя воспользоваться — решает сервер: в состоянии PKCE
   (`auth:telegram:pkce:<state>`) записано назначение, `login` или `link`, и
   код одного не завершит другое. До 04.09.2026 привязка просила у Telegram
   адрес `/settings`, которого в Allowed URLs нет, и Telegram отвечал
   «redirect_uri required». Если вы уже добавили вторую строку с `/settings` —
   её можно убрать, она больше ни на что не влияет.

> Публичный домен появился 2026-08-16 вместе с развёртыванием, поэтому шаг 1
> больше ничем не блокируется. Живой вход по-прежнему не проверен: у нас нет
> ваших учётных данных BotFather.

## Шаг 2. Применить схему к базе

> **На развёрнутом инстансе это уже сделано.** База создавалась пустой, схема
> применена целиком, `TELEGRAM` в enum есть. Раздел ниже нужен для любой другой
> базы — локальной или той, что появится позже.

Значение `TELEGRAM` есть в `schema.prisma`, но в самой базе его нет. Пока оно не
применено, первый же вход упадёт при создании пользователя: PostgreSQL не знает
такого значения enum.

**На локальной или одноразовой базе:**

```bash
pnpm run prisma-db-push
```

**На базе с реальными данными — не этой командой.** В `prisma-db-push` зашит
`--accept-data-loss`. Добавьте значение вручную, это безопасная и обратимая
операция:

```sql
ALTER TYPE "Provider" ADD VALUE IF NOT EXISTS 'TELEGRAM';
```

Проверить, что получилось:

```sql
SELECT unnest(enum_range(NULL::"Provider"));
```

В выводе должны быть `LOCAL`, `GITHUB`, `GOOGLE`, `FARCASTER`, `WALLET`,
`GENERIC` и `TELEGRAM`. Значение `WALLET` остаётся намеренно: вход по кошельку
убран, но старые записи пользователей на него ссылаются.

## Шаг 3. Положить значения в окружение

На сервере это `/srv/content-factory-next/app.env` (режим `600`, вне Git). Локально —
`.env` в корне репозитория, тоже не коммитится.

```
TELEGRAM_CLIENT_ID="<client id из шага 1>"
TELEGRAM_CLIENT_SECRET="<client secret из шага 1>"
```

Проверьте заодно, что `FRONTEND_URL` совпадает с тем, что вы внесли в Allowed
URLs, — из него собирается адрес возврата.

Секрет не должен попасть в Git, в промт, в аргумент команды и в лог. Задавайте
его в файле окружения или в секрет-хранилище платформы.

## Шаг 4. Перезапустить и проверить

На сервере переменные читаются при старте, пересборка не нужна:

```bash
cd /srv/content-factory-next && docker compose up -d cf-app
```

Локально:

```bash
pnpm run build
pnpm run pm2-run     # либо ваш способ запуска
```

Признаки успеха, по порядку:

1. На `/auth` рядом с остальными способами появилась кнопка «Войти через
   Telegram». Если её нет — не заданы обе переменные (кнопка требует пару).
2. Нажатие уводит на `oauth.telegram.org`, а не показывает ошибку. Если ошибка —
   расходится client id.
3. После подтверждения в Telegram вас возвращает в продукт уже внутрь. Если
   возврат приводит на страницу входа с ошибкой — расходится Allowed URL.
4. Второй вход тем же аккаунтом Telegram попадает в ту же организацию, а не
   создаёт новую.
5. «Настройки → Способы входа» → «Подключить» у Telegram: браузер уходит на
   `oauth.telegram.org`, возвращается на `/auth?provider=TELEGRAM`, сам уходит
   дальше в настройки, и Telegram в списке отмечен как подключённый. Ошибка
   «redirect_uri required» здесь означает, что в Allowed URLs стоит не тот
   адрес, что в `FRONTEND_URL`.

## Чего ожидать локально

Вход через провайдера **не работает при `NOT_SECURED=true`**, и это не поломка.
Возврат из Telegram привязан к браузеру через cookie `oauth_state`
(HttpOnly, Secure, `SameSite=None`, пять минут). Фронтенд и бэкенд живут на
разных портах, а в режиме `NOT_SECURED` браузерный запрос идёт без учётных
данных, поэтому cookie не доедет и обмен кода будет отклонён.

Это осознанный размен: без такой привязки чужой человек может пройти
аутентификацию сам и подсунуть вам ссылку возврата, после чего ваш браузер
окажется залогинен в **его** учётную запись. Для обычного локального запуска
используйте LOCAL-регистрацию, как описано в
[Локальной разработке](../development/local-development.md).
