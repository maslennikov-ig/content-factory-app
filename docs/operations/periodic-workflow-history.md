# История периодических процессов

Этап `content-factory-next-dbxe.20` ограничивает работу внутри одного запуска
Temporal. После порога процесс использует `continueAsNew`: идентификатор
workflow остаётся прежним, новый запуск получает новую историю и переданное
состояние. Это поддерживаемый механизм [Temporal](https://docs.temporal.io/develop/typescript/workflows/continue-as-new),
проверенный также по установленному TypeScript SDK 1.15.0.

| Новый workflow | Работа за запуск | Сохраняемое состояние / действие |
| --- | --- | --- |
| `autoPostWorkflowV2` | 100 часовых проходов | исходный `id`, `immediately=true`; прежний `autoPost` |
| `autoPostDraftV3Workflow` | 100 часовых проходов | `id`, `organizationId`, `immediately=true`; прежний `autoPostDraftV2` |
| `missingPostWorkflowV109` | 100 часовых проверок | без аргументов; прежний `searchForMissingThreeHoursPostsV108` |
| `sendEmailWorkflowV3` | 30 обработанных попыток | вся ожидающая очередь; прежний `sendEmailV2` с языком |

100 — размер партии по существующему подходу проекта, а не измеренный предел
сервера. Почтовый порог 30 сохраняет прежнее намерение V2, но теперь учитывает
и ошибку после исчерпания политики повторов. Отправленное или окончательно
неудачное письмо не переносится обратно в очередь; прежняя ошибка видна в
истории и workflow-логе. Дополнительного повтора отправки этот этап не вводит.
Отмена процесса распространяется дальше и не превращается в обычную ошибку.

Автопостинг перед продолжением выдерживает последний часовой интервал.
`immediately=false` пропускает только первый проход исходного запуска; следующий
запуск получает `true`, поэтому дополнительного пропуска или немедленного
повторного вызова на границе нет. Ошибка активности draft/recovery остаётся
фатальной, как раньше. Обычная ошибка legacy AutoPost допускает следующий
часовой проход, но учитывается в пороге.

Почтовая очередь сохраняет 700 мс между попытками, прежние ограничения повторов,
`top`/`bottom`, `replyTo` и `language`. Обработчик сигнала синхронный, а
продолжение вызывается из основного цикла после паузы. Полученные во время
последней отправки или паузы письма уже входят в передаваемую очередь.

## Места запуска и существующие экземпляры

Проверены реальные исходники `AutopostService.processCron/processCronV2`,
`InfiniteWorkflowRegister.onModuleInit` и `EmailService.sendEmail`.

| Потребитель | Новый тип для свежего запуска | Прежний workflow ID / политика |
| --- | --- | --- |
| Legacy AutoPost | `autoPostWorkflowV2` | `autopost-${id}`, прежний отказ при уже работающем экземпляре |
| Draft V2 | `autoPostDraftV3Workflow` | `autopost-draft-v2-${id}`, прежний отказ при уже работающем экземпляре |
| Recovery при `RUN_CRON` | `missingPostWorkflowV109` | `missing-post-workflow-v108`, `USE_EXISTING` |
| Асинхронная почта | `sendEmailWorkflowV3` | `send_email_v2`, прежний `signalWithStart` / `USE_EXISTING` |

On 11 October the owner authorized and root completed the actual mail singleton
cutover after proving the old V2 run empty and admission quiescent. V3 is now
served by the deployed worker under the same ID. Historical bodies remain
unchanged; see [the exact procedure and evidence](mail-queue-cutover.md). The
live cutover uses no synthetic mail and does not infer bounded behavior from
four initial events: the thirty-attempt bound is separately proved with the
matching native workflow and fake provider.

Суффикс прежнего ID сохранён намеренно: новый singleton ID мог бы создать ещё
один процесс рядом с уже работающим. Уже запущенный V2 почтовый workflow
получает сигнал даже если вызывающий теперь указывает V3. Его последующие
продолжения сохраняют V2; изменения селектора недостаточно для миграции такого
экземпляра. Recovery также продолжает существующий запуск. Прежние явные
действия пользователя «выключить/удалить автопостинг» сохраняют свои цели.

Все исторические workflow/активности и их экспорты сохранены. В этом этапе нет
принудительной замены, отмены живых процессов, новой активности или изменения
публикации V108. Старый комментарий в `content-lead-check.workflow.ts` о наличии
rotation у draft V2 не описывает фактическую реализацию; исходник исторического
контракта сохранён, ротация добавлена отдельным draft V3.

## Проверка и следующий выпуск

Локальные проверки используют реальные функции с виртуальными часами для двух
последовательных часовых запусков и потоков писем. Отдельный изолированный
Temporal подтверждает смену Run ID, сохранение очереди и сигналов, 30 неудачных
попыток до продолжения, отсутствие повторов в синтетическом наборе и доставку
нового селектора существующему V2. Истории старых периодических типов
воспроизводятся новым SDK bundle. Реальные почтовые/социальные провайдеры не
вызываются. Результат: [outcome](../../.codex/stages/content-factory-next-dbxe-periodic-history-stage/outcome.md).

Перед отдельно выбранной выкладкой `.8` проверить фактические активные
экземпляры, их типы, очередь и потребителей. Новый код сам не переводит старые
истории на новые типы. Живой размер истории, серверные ограничения и срок до
их достижения здесь неизвестны; инцидент не утверждается. Переключение или
завершение старого экземпляра требует отдельного решения с сохранением его
работы; массового перезапуска нет.

При откате сохранять экспорты новых типов, если они уже запущены, и их ожидающую
очередь. Ограничение обработанной работы за запуск не задаёт размер очереди,
политику архивного хранения всей цепочки или защиту от произвольного потока
невалидных сигналов.
