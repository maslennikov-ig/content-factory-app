# Очистка legacy Errors

Таблица `Errors` — история отказов публикации, а не второй сборщик исключений.
Новый код сохраняет в ней только платформу, идентификатор поста, время и
безопасную классификацию ошибки. Тело публикации, произвольный ответ провайдера,
секреты и данные пользователей в новые строки не попадают. Админская статистика
по числу ошибок и история конкретного поста сохраняются.

Срок хранения — **90 дней**. Скрипт
`scripts/operations/cleanup-legacy-errors.cjs` одновременно:

- удаляет строки старше 90 дней;
- заменяет содержимое оставшихся старых строк на `Unknown Error` или
  `Publishing failed`;
- всегда начинает с dry-run и выводит только количества, без содержимого строк;
- выполняет apply в одной транзакции и после него повторяет проверку.

Скрипт идемпотентен: успешный повторный запуск показывает нули и ничего не
меняет. Он не изменяет Prisma-схему и не использует `prisma db push`.

## Одноразовая очистка после выпуска безопасной записи

Сначала выпустите образ с новым кодом. Это исключает ситуацию, когда старый
процесс снова пишет полный ответ провайдера после очистки. Затем сделайте
резервную копию по `docs/operations/postgres-backup.md` и из каталога
`deploy/production` выполните только dry-run:

```bash
docker compose exec -T cf-app \
  node scripts/operations/cleanup-legacy-errors.cjs
```

Проверьте `expired`, `unsafeUnknown` и `unsafeKnown`. Отчёт не содержит тексты
постов, адреса или секреты. Применение — отдельное действие владельца:

```bash
docker compose exec -T \
  -e CF_CONFIRM_LEGACY_ERRORS_CLEANUP=apply \
  cf-app node scripts/operations/cleanup-legacy-errors.cjs --apply
```

Команда должна завершиться с нулевыми значениями в `verification`. После неё
повторите dry-run. При ненулевой проверке скрипт завершится с ошибкой; сохраните
резервную копию и расследуйте причину до повтора.

## Регулярное исполнение retention

Запускайте ту же apply-команду ежедневно из существующего планировщика хоста.
Она удаляет только строки с `createdAt` строго раньше границы 90 дней. Одновременная
новая публикация имеет более позднее время и под удаление не попадает. Если
`cf-app` остановлен, запуск должен считаться неуспешным и повториться по обычной
политике планировщика; отдельный контейнер или доступ к базе скрипту не нужны.

Увеличить или уменьшить окно для проверяемого разового запуска можно параметром
`--retention-days=N`. Постоянное изменение 90-дневной политики требует изменения
константы, теста и этого runbook в одном выпуске.
