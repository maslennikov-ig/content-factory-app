# Создание секций существующего сборщика без очистки данных

**Статус:** подготовлено для проверки и установки владельцем. Само наличие этого файла не означает, что таймер установлен или сбор ошибок непрерывно работает.

Существующий общий GlitchTip 6.0.5 хранит события в ежедневных секциях PostgreSQL 18: сначала диапазон UUIDv7 по времени приёма, затем четыре блока по организации. Штатный `maintain_partitions` одновременно создаёт секции и удаляет старые данные всех проектов. Для ограниченного исправления общего сборщика его запуск не подходит. Новый [скрипт](../../scripts/operations/collector-partitions-create-only.py) использует только генератор CREATE из установленного коллектора; срок хранения, другие таблицы, очередь задач и контейнеры он не меняет.

За один запуск проверяются сегодняшний день UTC и следующие шесть дней. Корректные существующие секции пропускаются, включая уже заполненные. Для недостающего дня создаются родитель и h0–h3 в одной транзакции; максимум — 35 таблиц и их автоматически унаследованные зависимости за запуск. Неверные границы, неполные дочерние блоки, коллизии имён, DEFAULT, изменённые исходники/настройки/схема или занятые блокировки приводят к отказу. Незнакомую секцию скрипт не исправляет и не удаляет.

По умолчанию скрипт строит план в транзакции READ ONLY. Запись требует явного `--apply`. Дату можно закрепить через `CF_COLLECTOR_PARTITIONS_NOW=2026-10-01T22:00:00Z`; допустим только явный UTC. В обычном таймере переменная пуста, и базу берёт `datetime.now(timezone.utc)`. Часы не зашиты в тестовые имена.

Создание нового дня кратко блокирует общую таблицу событий всех проектов. Применяется try-advisory lock `(1128682324,1)`, `LOCK TABLE ONLY ... NOWAIT`, предел ожидания блокировки 1 с, запроса 5 с и всей транзакции дня 5 с. Внешние ограничения задаются только для этого запуска. Штатное обслуживание не участвует в advisory lock; конфликт определяется блокировкой БД и проверкой каталога. Нет автоматического цикла повторов или увеличения сроков ожидания. Копирование внешних ключей может также кратко блокировать таблицы issue/organization/release. Старые строки не переписываются. [PostgreSQL 18: CREATE TABLE](https://www.postgresql.org/docs/18/sql-createtable.html), [LOCK](https://www.postgresql.org/docs/18/sql-lock.html), [ограничения времени](https://www.postgresql.org/docs/18/runtime-config-client.html).

## Проверка перед установкой

Источник проверки версии — снятые непосредственно с работающего коллектора исходники, а не устаревший статус в [описании сбора ошибок](error-collection.md). В скрипте закреплены SHA-256 четырёх файлов GlitchTip 6.0.5. Требуются PostgreSQL 18, прежние поля/индексы/внешние ключи `public.issue_events_issueevent`, владелец и соединение `postgres`, четыре блока и эффективные event/file lifetime 90 дней. Установка не сокращает общий срок до 30 дней. Обновление коллектора или схемы требует новой проверки и пересмотра этих условий; разрешающих обходов нет.

Фокусированная проверка с реальной временной PostgreSQL 18:

```bash
CF_COLLECTOR_PARTITIONS_EXECUTION_TEST=1 \
CF_COLLECTOR_PARTITIONS_TEST_REPORT=.codex/stages/content-factory-next-0qgn-collector-refresh/pg18-report.json \
uv run --no-project --with 'django==6.0.2' --with 'psycopg[binary]==3.3.2' \
  python3 -m unittest tests/test_collector_partitions_create_only.py -v
```

Проверка создаёт только собственный временный локальный контейнер с PostgreSQL 18, данными в tmpfs и случайным портом, доступным лишь на 127.0.0.1. Docker volumes не создаются. В конце удаляется ровно контейнер с проверенной меткой владельца. Существующие базы, контейнеры, провайдеры и аккаунты не используются. Проверяются повторный запуск, все четыре блока, сохранение старых строк/таблиц/90-дневного срока, неверные границы и коллизии, блокировки, ошибка посреди транзакции и её общий предел времени. Форма SQL в этом тесте воспроизводит снятый native-генератор; реальный импорт Django/native-кода отдельно проверяется планом READ ONLY в существующем контейнере.

## Предлагаемый пакет установки

Его готовит стадия `content-factory-next-0qgn-collector-refresh`. Пакет и журналы проверки находятся в её `install-packet/` и манифесте. Установка — отдельное действие владельца после проверки исходников и хешей. Этот скрипт не устанавливает сам себя.

Ровно четыре новых файла, все `root:root`:

| Источник | Новый путь на хосте | Права |
| --- | --- | --- |
| `scripts/operations/collector-partitions-create-only.py` | `/usr/local/lib/cf-collector-partitions-create-only/collector-partitions-create-only.py` | `0644` |
| `install-packet/cf-collector-partitions-create-only` | `/usr/local/sbin/cf-collector-partitions-create-only` | `0755` |
| `install-packet/cf-collector-partitions-create-only.service` | `/etc/systemd/system/cf-collector-partitions-create-only.service` | `0644` |
| `install-packet/cf-collector-partitions-create-only.timer` | `/etc/systemd/system/cf-collector-partitions-create-only.timer` | `0644` |

Включение таймера создаёт только его собственные служебные пути: `/etc/systemd/system/timers.target.wants/cf-collector-partitions-create-only.timer` и `/var/lib/systemd/timers/stamp-cf-collector-partitions-create-only.timer`. Существующие файлы, drop-in каталоги этих двух unit и любые одноимённые установленные unit — повод остановиться, а не перезаписать их. Временный каталог передачи — `/tmp/cf-collector-partitions-install-1da9d24b13a3`, новый `root:root` с правами `0700`; в нём допускаются только четыре файла из таблицы и `SHA256SUMS`. После сверки удалить можно только эти пять файлов, затем сам пустой каталог через `rmdir`. Журнал systemd хранит краткие JSON с датами/числом таблиц/кодом отказа, без событий, DSN, паролей или параметров соединения.

Порядок владельца:

1. Проверить коммит, манифест, исходники и выполнение теста. На хосте подтвердить отсутствие перечисленных путей/drop-in и `LoadState=not-found` для двух unit. Сверить исходники коллектора, срок хранения, его контейнер/image/start time и определения/строки старых таблиц с собственной свежей исходной проверкой.
2. Передать четыре файла в новый изолированный каталог. Сверить их SHA-256. Выполнить план **без `--apply`**, передав Python-файл на stdin в `docker --host unix:///var/run/docker.sock exec -i -w /code glitchtip-web-1 python -`. Не менять compose, `.env`, установленный код, штатные задачи или контейнер. План не доказывает фактического применения.
3. Если пути всё ещё отсутствуют, создать только `/usr/local/lib/cf-collector-partitions-create-only/` и установить четыре файла с правами из таблицы. Проверить установленную копию по хешам и `systemd-analyze verify` для двух файлов unit. После этого выполнить `systemctl daemon-reload`.
4. Включить только `cf-collector-partitions-create-only.timer` через `systemctl enable --now`, затем явно выполнить `systemctl start cf-collector-partitions-create-only.service` для первого обновления. При первом включении без stamp systemd 255 ждёт следующей календарной даты, даже если сегодняшний срок 00:05 уже прошёл; `Persistent=true` догоняет пропуск при существующем старом stamp. Не создавать искусственный stamp. Это следует из [исходников timer.c версии 255](https://raw.githubusercontent.com/systemd/systemd/v255/src/core/timer.c) (`timer_start`, строки 581–621; выбор календарной базы, 363–375) и [описания таймеров](https://raw.githubusercontent.com/systemd/systemd/v255/man/systemd.timer.xml). Включение таймера может запустить service, если календарный срок наступит в процессе установки; дополнительный явный запуск безопасно проверит и пропустит уже созданные секции. UTC в календарной строке поддерживается [форматом времени той же версии](https://raw.githubusercontent.com/systemd/systemd/v255/man/systemd.time.xml).
5. Проверить код завершения, краткий JSON, весь диапазон семи дней и четыре блока, а также сохранение исходников, срока хранения, старых определений/строк и image/start time контейнеров. Записать доказательства установки отдельно от локального теста. Проверить следующий календарный срок и успешный следующий ежедневный запуск. Следить за `systemctl is-failed cf-collector-partitions-create-only.service` и кодом завершения этого unit: timer сам по себе не подтверждает, что helper смог выполнить работу.

Если установка приходится на 2026-10-02 UTC при существующем покрытии 1–7 октября, первый план покажет только пять новых таблиц для 8 октября. Применение создаст ровно их; итоговая верхняя граница станет 2026-10-09T00:00Z. На другую дату принять фактический план, сверив сегодняшний UTC и предел семи дней. Это расчёт из диапазона, а не доказательство выполненного применения.

Service запускается от root только из-за доступа к локальному Docker socket; приложение внутри существующего контейнера получает свои прежние DB-права. Новый Python-процесс ненадолго использует память того же контейнера, поэтому реальный запас памяти и длительность проверяет владелец на установленном хосте. На хосте нет файлов с credentials: используется прежняя конфигурация collector. Helper фиксирует локальный Docker socket и имя `glitchtip-web-1`, чтобы окружение командной строки не направило его в другой Docker context. Флаг Docker `--config` указывает на собственный новый каталог helper, где нет `config.json`; закрытый настройкой `ProtectHome` домашний Docker config не нужен и не читается.

## Откат

Сначала отключить только новый таймер: `systemctl disable --now cf-collector-partitions-create-only.timer`. Если oneshot уже выполняется, дождаться его завершения и подтвердить, что service не активен; отключение таймера само по себе не отменяет текущий запрос. Не удалять файлы во время выполнения.

Сверить, что установленные файлы всё ещё принадлежат этому пакету и соответствуют его хешам; иначе остановиться. Удалить только четыре перечисленных файла, оставшуюся собственную enable-ссылку и собственный stamp, если они были созданы этим пакетом. Пустой новый каталог helper можно удалить через `rmdir`, затем выполнить `systemctl daemon-reload`. Другие unit, файлы коллектора/compose/env, контейнеры, задачи, настройки и таблицы не затрагиваются.

До COMMIT ошибка откатывает только текущий день. Уже успешно созданные секции **оставить**: после фиксации там могли появиться события любого проекта. Откат таймера никогда не включает DROP, DETACH, очистку строк или восстановление старой БД. Пропущенные прошлые дни и повтор упавших задач — отдельные явно ограниченные действия владельца.
