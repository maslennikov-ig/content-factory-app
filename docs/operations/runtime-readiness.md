# Проверки готовности runtime

**Аудитория:** оператор Content Factory. **Статус:** код `0qgn.5` принят root
и включён в рабочую ветку 2 октября; новая выкладка и проверка работающей версии
ещё требуются. Документ описывает контракт кода и не подтверждает здоровье production,
готовность SaaS или разрешение на операции с хостом.

## Маршруты

Внутри backend маршруты начинаются с `/monitor`; nginx добавляет внешний
префикс `/api`. Они доступны без пользовательской сессии.

| GET | Успех | Отказ |
| --- | --- | --- |
| `/api/` | 200, прежняя строка `App is running!` | прежнее поведение |
| `/api/monitor/ready` | 200, `{"status":"success","message":"Runtime dependencies are ready."}` | 503, `{"status":"error","message":"Runtime dependencies are unavailable."}` |
| `/api/monitor/queue/:name` | 200, прежние два поля: `{"status":"success","message":"Queue telegram is healthy."}` для telegram | известная недоступная очередь: 503, `{"status":"error","message":"Queue is unavailable."}`; неизвестное имя: 404, `{"status":"error","message":"Unknown queue."}` |

Docker HEALTHCHECK, переключение образа и удержание артефактов продолжают
использовать существующий liveness `/api/`. Readiness — отдельный сигнал.
Получение 503 на новом маршруте не перезапускает контейнер, не запускает
публикацию и не меняет действующие правила rollback.

После внедрения точной версии оператор может выполнить один разрешённый
readback внутри контейнера приложения:

```bash
curl --max-time 3 -i http://127.0.0.1:5000/api/monitor/ready
curl --max-time 3 -i http://127.0.0.1:5000/api/monitor/queue/main
```

Проверку связывают с фактическим image/source, процессом и портом. Эти команды
не были выполнены при подготовке изменения; периодический live polling не добавлен.

## Что проверяется

`/monitor/ready` использует уже существующие клиенты приложения:

- `PrismaService.organization.findFirst({select:{id:true}})` проверяет чтение
  через runtime роль и подключение приложения. Пустая таблица допустима.
  ID остаётся внутри вызова и не попадает в ответ или cache.
- Действующий Redis-клиент должен быть в состоянии `ready` и ответить
  `PONG` на настоящий PING. Отсутствующая конфигурация с фактическим
  `MockRedis`, отключение, ошибка или иной ответ означают отказ.
- Действующее Temporal-соединение должно вернуть SERVING и описание namespace
  с именем, которое настроено в SDK-клиенте. Namespace передаётся явно каждому
  RPC; наличие объекта клиента или библиотечный `getHealth()` недостаточны.
- В `main` нужны свежие pollers обоих типов: workflow и activity.
  Постовые и аналитические workflows используют main также для activities.

Очереди берутся из `main` и существующих provider-идентификаторов по тем же
правилам, что у worker-конфигурации. Имена с дефисом не создают отдельную очередь.
Неизвестное имя отклоняется до I/O и выделения cache-записи. Регистр имени
должен совпадать с каноническим идентификатором.

`/monitor/queue/:name` проверяет Temporal и pollers конкретной известной
очереди: оба типа для main, только activity для provider. БД и Redis этим
маршрутом не проверяются. `EXCLUDE_QUEUE` задаёт размещение локального worker;
свежий poller на другом worker-хосте может подтвердить ту же очередь.

Для каждого нужного типа достаточно одного poller с корректным
`lastAccessTime` не из будущего и возрастом не больше **120 секунд** в момент
проверки. Отсутствие, неизвестная форма или некорректная дата не превращаются
в успех. Проверка отражает metadata, а не выполнение пользовательской задачи.

## Время, cache и отказ

Ожидание зависимостей ограничено бюджетом **2 секунды**. Temporal RPC получают
реальный deadline на общем соединении. Результаты успеха и отказа сохраняются
на **5 секунд** и повторные запросы объединяются. Поэтому ответ может отражать
предыдущую проверку в пределах этого окна, включая свежесть poller на тот момент.

Cache содержит только database, redis и фиксированный набор известных очередей.
Этот cache и объединение запросов действуют в одном backend-процессе; реплики
проверяют зависимости самостоятельно.
В нём остаются boolean, срок и состояние незавершённой проверки; строки БД,
poller identities, адреса, настройки и ошибки не сохраняются. Ответы отказа
содержат только фиксированные status/message, без причин и секретов.

Таймаут ответа не отменяет Prisma/PING. Пока реальный вызов не завершился,
новые запросы не запускают заменяющий вызов для той же зависимости даже после
истечения cache. Поздняя ошибка наблюдается; поздний успех не переписывает
отказ. После завершения вызова и истечения окна можно выполнить новую проверку.
Зависший навсегда вызов продолжит давать отказ до завершения или штатного
перезапуска процесса: monitor не закрывает общий клиент для «восстановления».
Блокировка event loop может задержать HTTP-ответ; поздний результат всё равно
не принимается как успех бюджета.

Новых клиентов, отдельных соединений, интервалов, ключей Redis, записей БД,
workflows, activities и provider/model-вызовов monitor не создаёт.
Он использует транспорт действующих клиентов, включая их существующее
поведение внутри заданного Temporal deadline.

## Границы доказательства

Успешная readiness подтверждает этот ограниченный набор зависимостей.
Она не доказывает backlog, доставку публикации, пригодность provider credentials,
доступность media/storage, правильность квот, финансовую сверку AI-ledger,
межтенантную изоляцию, backup/restore или общую готовность SaaS.

Error collection остаётся отдельным необязательным путём. Отказ GlitchTip
не переводит core readiness в отказ. Наличие SDK/DSN/маршрута и HTTP 202 relay
не подтверждают приём, хранение, retention или уведомление оператора.

Исходные проверки в `tests/runtime-monitor.readiness.test.cjs` используют
настоящие controller/service и Nest HTTP с подставленными зависимостями;
они не обращаются к production и не заменяют root-owned readback после
внедрения. Код:
`apps/backend/src/services/monitor/runtime-monitor.service.ts`,
`apps/backend/src/api/routes/monitor.controller.ts`;
DI-регистрация: `apps/backend/src/api/api.module.ts`.
