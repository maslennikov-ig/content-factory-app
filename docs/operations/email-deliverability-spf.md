**Статус:** справка для владельца, действие не выполнено намеренно.
**Дата проверки:** 2026-09-01.
**Кто может изменить DNS:** только владелец домена `aidevteam.ru` в панели регистратора. У меня нет и не должно быть доступа к DNS, я ничего не менял.

## Главный вывод: перепроверка отменяет часть исходного диагноза

Вводные данные от 01.09.2026 говорили, что SPF на `smtp.aidevteam.ru` отсутствует. Это было верно для запроса SPF-записи **на самом `smtp.aidevteam.ru`** — но Resend по умолчанию кладёт SPF- и MX-записи не на корень добавленного домена, а на его поддомен `send.<домен>` (это его механизм Return-Path/bounce-обработки). При проверке `send.smtp.aidevteam.ru` записи нашлись, и они корректны:

- `send.smtp.aidevteam.ru` TXT: `v=spf1 include:amazonses.com ~all` — есть.
- `send.smtp.aidevteam.ru` MX: `10 feedback-smtp.eu-west-1.amazonses.com.` — есть, регион `eu-west-1`.

Это совпадает с записью в [`outbound-connections.md`](outbound-connections.md), сделанной 19.08.2026: домен был подключён к Resend, регион отправки — `eu-west-1`, «SPF и MX для отчётов о доставке лежат на поддомене `smtp`» (что в точности означает `send.smtp.aidevteam.ru`, а не буквально `smtp.aidevteam.ru`). Формулировка в том документе не проговаривала явно «поддомен `send.` от `smtp`», из-за чего 01.09 при проверке смотрели не туда.

**Вывод: DNS для отправки через Resend настроен так, как Resend это ожидает. Здесь нечего чинить.** Ниже — полная перепроверка по всем пунктам, документация Resend, разбор DMARC и, отдельно, что тогда может быть настоящей причиной попадания в спам.

## 2. Документация Resend, на которую я опирался

Даты публикации на страницах Resend по большей части не проставлены (проверено WebFetch — «дата обновления не указана»), кроме одной. Указываю источники прямо:

- [`resend.com/docs/dashboard/domains/introduction`](https://resend.com/docs/dashboard/domains/introduction) — общий обзор: субдомен рекомендуется вместо корневого домена ради изоляции репутации; упоминает регионы, Custom Return Path, DMARC, BIMI.
- [`resend.com/docs/knowledge-base/what-if-my-domain-is-not-verifying`](https://resend.com/docs/knowledge-base/what-if-my-domain-is-not-verifying) — описывает деление на «старые» домены (TXT+MX для SPF) и домены, созданные **после августа 2026** (у них вместо TXT+MX может быть пара CNAME-записей, статус `partially_verified` при частичной верификации). MX для отправки: `feedback-smtp.<регион>.amazonses.com`, где `<регион>` фиксируется при создании домена и не меняется.
- [`resend.com/changelog/custom-return-path`](https://resend.com/changelog/custom-return-path) (запись от **15.05.2025**) — раньше hostname для SPF/MX-записей был жёстко зашит как `send.<домен>`; фича Custom Return Path позволяет задать произвольное имя поддомена вместо `send`. Раз в нашем случае записи нашлись именно на `send.smtp.aidevteam.ru`, кастомный Return Path для этого домена не задавался — используется значение по умолчанию.
- [`github.com/resend/resend-skills`](https://github.com/resend/resend-skills/blob/main/skills/resend/references/domains.md) — справочник по доменам: подтверждает четыре региона (`us-east-1`, `eu-west-1`, `sa-east-1`, `ap-northeast-1`), MX-хост вида `feedback-smtp.{region}.amazonses.com`, и что `customReturnPath` (например, `bounce`) формирует адрес вида `bounce@send.<домен>` для DMARC-выравнивания.
- Совокупность руководств Resend по провайдерам (Cloudflare, IONOS, Namecheap, GoDaddy, Vercel, Route 53 — все под `resend.com/docs/knowledge-base/<provider>`) единообразно описывает: имя узла для MX — `send`, приоритет `10`, TTL обычно оставляют по умолчанию (у большинства провайдеров это означает 3600 сек / «Auto»); имя узла для DKIM — `resend._domainkey` (без домена в конце — почтовая панель просит вставить значение, которое Resend показывает, «как есть»).

**Развилка EU/US, которую нужно назвать честно:** конкретный MX-хост (`feedback-smtp.eu-west-1.amazonses.com` против `us-east-1` и т. д.) зависит от региона, выбранного при добавлении домена в Resend, и не виден заранее «по документации» — только по факту в DNS или в панели Resend. У нас регион уже определился по факту в DNS и по записи в `outbound-connections.md`: **`eu-west-1`**. Значение SPF-TXT (`v=spf1 include:amazonses.com ~all`) от региона не зависит — это одна и та же строка для всех регионов Resend, потому что вся отправка идёт через Amazon SES.

## 4. DMARC — отдельный вопрос, отдельная рекомендация

Сегодня: у `smtp.aidevteam.ru` нет собственной записи `_dmarc`, поэтому применяется унаследованная политика родителя — `_dmarc.aidevteam.ru` → `v=DMARC1; p=quarantine; rua=mailto:postmaster@aidevteam.ru`.

**Что это значит практически.** DMARC проверяет соответствие (alignment) SPF и/или DKIM домену в заголовке `From:`. У нас:
- DKIM подписан с `resend._domainkey.smtp.aidevteam.ru` — домен подписи совпадает с доменом `From:` (`smtp.aidevteam.ru`) буквально, DKIM-alignment проходит.
- SPF проверяется по домену из `Return-Path`/envelope-from, а это `send.smtp.aidevteam.ru`. При DMARC-выравнивании по умолчанию используется «relaxed»-режим (запись `aidevteam.ru` не задаёт `aspf=s`/`adkim=s`, значит действует relaxed): в этом режиме достаточно совпадения по «организационному домену», а не по точному хосту. `send.smtp.aidevteam.ru` и `smtp.aidevteam.ru` — оба под одним организационным доменом `aidevteam.ru`, так что SPF-alignment по правилам DMARC тоже должен проходить.

Это рассуждение по RFC 7489 и по тому, что стоит в DNS — **не то же самое, что реальный вердикт**. Единственное, что доказывает или опровергает это, — блок `Authentication-Results` из заголовков реально полученного письма (см. раздел 5).

**Нужна ли своя запись `_dmarc.smtp.aidevteam.ru`?**

- *Что она даст:* явный контроль политики именно для почты продукта, независимо от того, что стоит на `aidevteam.ru`; отдельный адрес для отчётов (`rua=`) — сейчас отчёты по несуществующей записи пойдут `postmaster@aidevteam.ru`, то есть смешаются с отчётами по остальному домену (сайты, другая почта владельца), если там вообще что-то ещё отправляется.
- *Чем рискует:* если поставить `p=reject` без разбега — а разбега (истории $ ) отправки с этого поддомена почти нет — можно молча ронять письма, которые не пройдут выравнивание по случайности (смена региона Resend, изменение Return-Path и т. п.), причём без единого предупреждения получателю.
- *Моя рекомендация* (не решение — решение за владельцем): начать с явной `_dmarc.smtp.aidevteam.ru` в режиме `p=none` с `rua=` на отдельный или тот же адрес, понаблюдать через отчёты пару недель, и только потом (если снова нужно ужесточение отдельно от родителя) поднимать до `quarantine`/`reject`. Если владелец не планирует расширять отправку с этого поддомена и не хочет отдельно администрировать записи — можно ничего не делать: унаследованный `p=quarantine` не хуже, чем `p=none`, и уже сейчас (см. предыдущий раздел) оба механизма alignment должны сходиться.

## 5. Проверка ПОСЛЕ любых действий владельца — по шагам

Даже если менять DNS не пришлось, этот раздел нужен: единственный способ подтвердить или опровергнуть роль ссылки на `localhost` — контрольная отправка с боевого инстанса.

### 5.1 Убедиться, что записи всё ещё видны в DNS

```
curl -s "https://dns.google/resolve?name=send.smtp.aidevteam.ru&type=TXT"
curl -s "https://dns.google/resolve?name=send.smtp.aidevteam.ru&type=MX"
curl -s "https://dns.google/resolve?name=resend._domainkey.smtp.aidevteam.ru&type=TXT"
curl -s "https://dns.google/resolve?name=_dmarc.aidevteam.ru&type=TXT"
```
Ожидается: те же значения, что в таблице раздела 1/3. Если добавляли свою `_dmarc.smtp.aidevteam.ru` — проверить и её тем же способом с `name=_dmarc.smtp.aidevteam.ru`.

### 5.2 Убедиться, что Resend видит домен как подтверждённый

В дашборде Resend → Domains → `smtp.aidevteam.ru`: статус должен быть `Verified` (не `Pending` и не `Failed`). Если когда-то стоял `partially_verified` — после любых правок нажать «Restart verification» в панели и подождать: по данным Resend, полная перепроверка может занимать до суток.

### 5.3 Контрольная отправка с БОЕВОГО инстанса — решающий шаг

Это единственная проверка, которая разделяет две конкурирующие причины (домен vs ссылка на `localhost`):

1. Зарегистрировать тестовый аккаунт **на `https://factory.aidevteam.ru`**, не на локальном стенде.
2. Получить письмо активации в Gmail (в любой папке, включая «Спам»).
3. Открыть письмо → меню из трёх точек → **«Показать оригинал»** («Show original»).
4. Найти блок `Authentication-Results:` в заголовках. В нём — три независимых вердикта:
   - `spf=pass` (или `fail`/`neutral`/`none`/`softfail`) — результат проверки Return-Path-домена относительно SPF-записи;
   - `dkim=pass` (или `fail`/`none`) — результат проверки подписи `resend._domainkey.smtp.aidevteam.ru`;
   - `dmarc=pass` (или `fail`) — итоговое совпадение по выравниванию, на основе двух предыдущих.
5. Успех — это **`dmarc=pass`**. Он возможен даже при `spf=fail`, если `dkim=pass` и выравнивание по DKIM сошлось (и наоборот) — DMARC требует, чтобы прошёл хотя бы один из двух с выравниванием, а не оба.
6. Отдельно проверить сам текст письма: ссылка активации должна вести на `https://factory.aidevteam.ru/auth/activate/<токен>`, а не на `http://localhost:4200/...`. Если увидите `localhost` — на боевом инстансе не настроен `FRONTEND_URL`, это отдельная и самостоятельная проблема конфигурации, не про DNS.

**Как читать результат:**
- Если `dmarc=pass` и ссылка ведёт на `https://factory.aidevteam.ru`, а письмо всё равно в спаме — причина не в аутентификации и не в ссылке; дело в репутации нового отправителя (первое письмо с домена, отсутствие истории), содержимом письма или в фильтрах конкретного почтового ящика. Это отдельная тема, не про DNS.
- Если `dmarc=fail` — это первое реальное доказательство проблемы аутентификации, и тогда стоит разбирать `spf=`/`dkim=` по отдельности, потому что общий вывод «DNS настроен верно» из разделов 1–4 не подтверждён живым письмом.
- Если ссылка ведёт на `localhost` — сначала чинить `FRONTEND_URL` в конфигурации боевого инстанса, потому что при живой ссылке на localhost результат теста будет искажён независимо от `dmarc=`.
