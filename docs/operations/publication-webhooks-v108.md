# Идентификатор публикации в webhook V108

Статус: подготовлено и проверено локально в dbxe.17, 10.10.2026.
Работающий сервис и реальные получатели этим этапом не проверялись.

## Формат события

Новый `postWorkflowV108` передаёт в `sendWebhooksV108` внутренний `Post.id`,
организацию и канал. Поиск проходит через PostsService и Prisma, проверяя
принадлежность Post и самого канала организации. Удалённая запись, комментарий,
неверный канал или чужая организация не получают пустое либо чужое событие:
доставка прекращается с видимой ошибкой.

Сохраняются JSON-массив и прежние поля. Заголовки:

```http
Content-Type: application/json
X-Content-Factory-Webhook-Version: 2
```

Синтетический пример:

```json
[
  {
    "id": "local-post",
    "providerPostId": "remote-post",
    "content": "Synthetic public text",
    "publishDate": "2000-01-01T00:00:00.000Z",
    "releaseURL": "https://synthetic.invalid/published",
    "state": "PUBLISHED",
    "integration": {
      "id": "local-channel",
      "name": "Synthetic",
      "providerIdentifier": "synthetic",
      "picture": null,
      "type": "social"
    }
  }
]
```

`id` — внутренний ID публикации Content Factory. `providerPostId` — отдельный
ID соцсети из сохранённого `releaseId`; при отсутствии он равен `null`.
`releaseURL` и `state` читаются из той же записи Post. `integration.id` —
внутренний ID канала, `providerIdentifier` — тип провайдера. Журнал публикации,
`organizationId`, токены и внутреннее имя `releaseId` в тело не попадают.

Выбираются активные webhook своей организации: пустой список каналов означает
все каналы, непустой — только перечисленные. При отсутствии подходящих webhook
активность возвращает нулевые счётчики без запроса Post и сетевого вызова.
Отдельный ручной endpoint `/webhooks/send` сохраняет прежний контракт.

## Доставка и ошибки

Используются прежний SSRF-safe dispatcher, ручная обработка перенаправлений и
сигнал отмены через 30 секунд. Существующее явное исключение
`DISABLE_SSRF_PROTECTION=true` сохраняется. Тело ответа отбрасывается.
Только HTTP 2xx считается подтверждением транспорта; 3xx не перенаправляется,
4xx/5xx и сетевые ошибки считаются неуспешной доставкой. Подтверждение транспорта
не доказывает обработку события приложением получателя.

Активность заканчивает все выбранные отправки и возвращает счётчики
`delivered`, `failed`, `skipped`. Если есть отказ, она завершается
`webhook_delivery_failed`; недоступный Post даёт `webhook_post_unavailable`.
Ошибки не допускают автоматического повтора; webhook proxy имеет одну попытку.
Неопределённый сетевой результат не является основанием повторять весь пакет.

Отказ виден в истории активности Temporal и журнале `webhook_delivery_failed`:
фиксированная причина и HTTP-статус, без адреса получателя, текста, токена или
исходного исключения. V108 перехватывает этот вспомогательный отказ и продолжает
автоматизации. Подтверждённая публикация остаётся опубликованной и не отправляется
заново. Отмена workflow продолжает останавливать исполнение и не подавляется
как обычная ошибка доставки. Гарантия ровно одной доставки при падении worker не вводится.

## Переход и откат при отдельно выбранном выпуске

Новые обычные запуски, recovery и повторные дети выбирают V108. Часовой loop —
`missingPostWorkflowV109`, ID — прежний `missing-post-workflow-v108`, флаг — прежний
`RUN_CRON`; [ротация истории](periodic-workflow-history.md) сохраняет активность V108.
Recovery сохраняет `USE_EXISTING`, фиксированный ID и атрибуты
организации: существующая история продолжает свою прежнюю версию.

Workflow/активности V101–V107 сохранены без изменения. Их старый webhook получает
прежний аргумент и может отправлять пустой массив; обновление не переписывает
историю. Не перезапускать подтверждённые публикации ради исправления webhook.

Перед будущим выпуском проверить внешних получателей на формат v2 и проверить
истории `missing-post-workflow`, `missing-post-workflow-v106`,
`missing-post-workflow-v107`. Управляемо завершить только проверенные старые
recovery-loop перед включением V108; регистратор сам их не останавливает.
Схема журнала и защита публикации остаются в
[правилах V106](publication-recovery-v106.md), сроки — в
[правилах автоматизаций](automation-deadlines.md). Обязателен исходный полный
выпускной gate dbxe.8. Локальная проверка dbxe.17 его не заменяет.

При откате остановить новые старты, сохранить V108 в worker до завершения её
историй и сохранить журнал подтверждений. Не возвращать неопределённые Post
старому writer. Совместимость реальных получателей и production-историй остаётся
отдельной проверкой выпуска.

## Локальная проверка

`tests/webhook-identity.test.cjs` вызывает настоящий workflow, активность,
сервис и Prisma-метод с синтетическими строками и fake HTTP: разные ID,
две организации/канала, поля и фильтры, HTTP/сетевая ошибка, безопасная диагностика,
сохранение одной публикации и продолжение действий.
[Offline SDK replay](../../.codex/stages/content-factory-next-dbxe-webhook-identity-stage/native-replay.cjs)
собирает текущий набор и воспроизводит семь сохранённых синтетических историй
V101–V107 из этапа .16. V108 собрана, но нативно в этом этапе не исполнялась.
Реальный получатель, база production и внешний провайдер не вызывались.
