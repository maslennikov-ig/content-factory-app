# Конфигурация

**Статус:** `current`
**Проверено:** 2026-08-18

Полный безопасный шаблон находится в [.env.example](../../.env.example).
В production конфигурация разделена: [env.example](../../deploy/production/env.example)
превращается в owner/Compose `.env`, а
[app.env.example](../../deploy/production/app.env.example) — в монтируемый только в
`cf-app` `app.env`. Значения в примерах не являются production secrets.

## Регистрация и вход

| Переменная                                                  | Поведение                                                                                                       |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `DISABLE_REGISTRATION`                                      | запрещает самостоятельную LOCAL регистрацию                                                                     |
| `CONTENT_FACTORY_REQUIRE_APPROVAL`                          | регистрация открыта, но новый аккаунт не работает до одобрения администратором; включает только значение `true` |
| `EMAIL_PROVIDER`                                            | выключатель доставки почты; см. «Доставка почты» ниже                                                           |
| `EMAIL_FROM_ADDRESS/NAME`                                   | отправитель email; без любого из двух отправка молча прекращается                                               |
| `NOT_SECURED`                                               | ослабляет secure cookie для локального HTTP; публично не использовать                                           |
| `AUTH_COOKIE_DOMAIN`                                        | область cookie; по умолчанию — точный хост из `FRONTEND_URL`                                                    |
| `GITHUB_CLIENT_ID/SECRET`                                   | GitHub login/OAuth                                                                                              |
| `CONTENT_FACTORY_GENERIC_OAUTH` и `CONTENT_FACTORY_OAUTH_*` | OIDC/OAuth provider вроде Authentik; включает только значение `true`                                            |
| `TELEGRAM_CLIENT_ID/SECRET`                                 | Telegram OpenID Connect; кнопка скрыта без полной пары                                                          |

Google login в текущей реализации использует `YOUTUBE_CLIENT_ID`/`YOUTUBE_CLIENT_SECRET`; default redirect — `${FRONTEND_URL}/integrations/social/youtube`. Он обязан точно совпадать с authorized redirect URI Google OAuth client.

Для Telegram login точный redirect URI — `${FRONTEND_URL}/auth?provider=TELEGRAM`, и в Allowed URLs у BotFather он один: привязка Telegram из «Настройки → Способы входа» с 04.09.2026 идёт через этот же адрес. Две разные вещи решают две разные стороны, и при разборе сломанной привязки их не надо путать. **Куда вернуть человека** решает браузер: вкладка, начавшая привязку, оставляет заметку в `sessionStorage` (`content-factory:identity-link-intent`, пять минут), страница `/auth` её читает и сама уводит на `/settings` с тем же `code` и `state` — до всякого обращения к серверу. В Redis этой заметки нет. **Чем нельзя воспользоваться** решает сервер: в состоянии PKCE (`auth:telegram:pkce:<state>`, те же пять минут) лежит признак назначения `purpose` — `login` или `link`, — и код, выданный для входа, привязку не завершит, а код привязки не даст войти. Если привязка обрывается на `/auth` и человек остаётся на странице входа — потеряна заметка вкладки; если запрос отклонён с «issued for a different purpose» — не совпало назначение. Client id и secret выдаются отдельно в настройках Login Widget у BotFather; `TELEGRAM_TOKEN` для публикации в каналы их не заменяет.

### Telegram support relay

`TELEGRAM_SUPPORT_OWNER_CHAT_ID` задаёт chat id владельца, которому общий
Telegram bot пересылает личные входящие сообщения. Relay использует тот же
`getUpdates` consumer, что `/connect` и сбор статистики: второй poller для этого
бота поднимать нельзя. Валидный `/connect <word>`, сообщения групп и
supergroup, обсуждения и channel posts владельцу не пересылаются.

В базе хранится только `update_id`, исходные chat/message id и состояние
доставки. Текст и вложения в outbox не копируются. Пустое значение безопасно
отключает доставку, но не приём: consumer пишет предупреждение, а новые личные
сообщения остаются в очереди до появления конфигурации. После задания значения
перезапустите backend; очередь будет обработана автоматически.

Порядок первого включения на сервере, ровно в этой последовательности:

1. Выкатите образ с relay и примените схему обычным путём из
   [production-deploy](production-deploy.md#применение-prisma-схемы). Relay
   опирается на таблицу `TelegramSupportRelayOutbox`. Пока её нет, consumer
   пишет в лог `TelegramSupportRelayOutbox does not exist` и просто не
   пересылает личные сообщения; `/connect`, статистика и обсуждения при этом
   работают. Как только схема применена, relay поднимается сам на следующем
   опросе — перезапуск не нужен. Проверка:
   `select to_regclass('public."TelegramSupportRelayOutbox"')` возвращает имя,
   а не `NULL`.
2. Владелец пишет боту любое личное сообщение.
3. Возьмите его chat id из очереди — текст сообщения там не хранится:
   `select "sourceChatId" from "TelegramSupportRelayOutbox" order by "updateId" desc limit 1;`
4. Впишите значение в `TELEGRAM_SUPPORT_OWNER_CHAT_ID` в `app.env` и
   перезапустите backend. Накопленная очередь уйдёт владельцу сама.

Значение — это не username и не id бота, а числовой chat id владельца; для
личной переписки он совпадает с его user id и может быть отрицательным только
для групп, которые сюда всё равно не попадают.

Доставка имеет семантику at-least-once: после ошибки запись остаётся в очереди
и повторяется, а авария между успешным Telegram API-вызовом и отметкой в БД
может дать дубликат. Telegram не пересылает некоторые service messages и
protected content. Такие записи не теряются и будут повторяться, но оператору
нужно разбирать предупреждения и при необходимости отвечать пользователю в
исходном чате вручную.

**Перед включением Telegram login схема БД должна знать значение `TELEGRAM`.** Enum `Provider` в [schema.prisma](../../libraries/nestjs-libraries/src/database/prisma/schema.prisma) содержит его в репозитории, но в базе оно появляется только после применения схемы. Пока значение не применено, первый вход завершится ошибкой при создании пользователя. Порядок и точные команды — в [Подготовка входа через Telegram](telegram-login-setup.md).

Возврат из провайдера привязан к браузеру: `GET /auth/oauth/:provider` кладёт `state` в cookie `oauth_state` (HttpOnly, Secure, `SameSite=None`, 5 минут), а обмен кода отклоняется, если cookie отсутствует или не совпадает. Cookie передаётся между разными origin фронтенда и бэкенда, поэтому при `NOT_SECURED=true` она не отправляется и вход через провайдера локально не работает — это ожидаемо, локально используйте LOCAL регистрацию. Так же ведут себя оба провайдера с `state`: TELEGRAM и GENERIC.

### Требования к паролю

Переменной для этого нет — правило зашито в DTO и действует всегда:

| Где | Правило | Источник |
| --- | --- | --- |
| Новая регистрация с `provider === 'LOCAL'` | 12..64 символа | [create.org.user.dto.ts](../../libraries/nestjs-libraries/src/dtos/auth/create.org.user.dto.ts) |
| Новая регистрация через провайдера | требование 12 символов не применяется: при `providerToken` пароль вообще не валидируется, иначе действует общий минимум 3 | там же, проверка привязана к `provider` |
| Установка пароля по ссылке восстановления | 12..64 символа | [forgot-return.password.dto.ts](../../libraries/nestjs-libraries/src/dtos/auth/forgot-return.password.dto.ts) |

Ограничение видит пользователь, а не только оператор: форма регистрации и
форма восстановления откажут более короткому паролю. Проверяется только
задаваемый пароль. Существующие хеши и вход по ним не перевалидируются, то
есть выданные раньше короткие пароли продолжают работать, пока человек не
сменит их сам; восстановление же поднимет такой пароль до 12 символов.
Восстановление вообще может задать только LOCAL-пароль: ссылка не выдаётся
аккаунту без входа по паролю.

### Ограничение частоты неаутентифицированных POST

Границы заданы в
[throttler.provider.ts](../../libraries/nestjs-libraries/src/throttler/throttler.provider.ts)
и переменными не настраиваются. Все окна — 60 секунд, и все счётчики — **на
одного вызывающего**, а не на инстанс:

| Маршрут | Лимит за 60 с |
| --- | --- |
| `POST /auth/register` | 1 |
| `POST /auth/login` | 10 |
| `POST /auth/forgot` | 5 |
| `POST /auth/resend-activation` | 3 |

`login` намеренно самый свободный: это тот маршрут, который человек повторяет,
опечатавшись в пароле, и через который заказывается работа bcrypt.
`resend-activation` — самый жёсткий: он ещё и отвечает на вопрос «существует ли
такой адрес», а три ответа в минуту делают перебор списка адресов
бессмысленным. Исчерпание даёт `429` и одну строку warning с именем маршрута —
без адреса, User-Agent и cookie.

Вызывающий определяется коротким HMAC от адреса соединения с ключом, который
живёт только в памяти процесса, и с минутной корзиной. Сырой адрес нигде не
сохраняется, а после перезапуска ключ другой и все корзины пустые.

#### Контракт с ingress: два прыжка до Nest

Счётчик работает только если до Nest доехал адрес настоящего клиента, а не
адрес соседнего прокси. Цепочка такая:

1. **Внешний ingress** (в этом развёртывании — Caddy на хосте) обязан
   **заменять**, а не дополнять `X-Real-IP` и `X-Forwarded-For`:
   [Caddyfile.snippet](../../deploy/production/Caddyfile.snippet) пишет в оба
   `{remote_host}`. Именно замена уничтожает значение, которое подделал
   браузер: до приложения оно не доходит.
2. **Nginx внутри контейнера** ([nginx.conf](../../var/docker/nginx.conf))
   передаёт дальше `X-Real-IP`, пришедший от ingress, и подставляет
   `$remote_addr` только когда заголовка нет — это случай прямого обращения к
   контейнеру, где `$remote_addr` и есть клиент. Обычная строка
   `proxy_set_header X-Real-IP $remote_addr` тут была бы ошибкой: она заменила
   бы клиента адресом Caddy, одинаковым для всех, и все вызывающие
   схлопнулись бы в одну общую корзину на весь инстанс.
3. **Nest** читает первый элемент `X-Forwarded-For`, затем `X-Real-IP`, затем
   адрес сокета. Nginx к `X-Forwarded-For` только дописывает, поэтому реальный
   клиент остаётся первым элементом при любом из двух вариантов.

Если ingress меняется, проверять надо именно свойство «замена, а не
добавление». Ingress, который дописывает заголовок, отдаёт управление
бюджетом вызывающему.

#### Что этот механизм не делает

- **Redis обязателен.** Хранилище счётчиков — Redis
  (`ThrottlerStorageRedisService` в `apps/backend/src/app.module.ts`), а клиент
  создан с `maxRetriesPerRequest: null`
  ([redis.service.ts](../../libraries/nestjs-libraries/src/redis/redis.service.ts)):
  пока соединения нет, команда не отклоняется, а ждёт. Недоступный Redis
  поэтому не открывает лимитируемые маршруты, а подвешивает их. Это отказ, а не
  обход, но в мониторинге он выглядит как зависший запрос, а не как `429`.
- **Корзина выровнена по минуте.** Окно — не скользящее. Вызывающий, который
  израсходовал лимит в конце минуты, получает свежий бюджет на её границе,
  то есть примерно двойной всплеск на стыке. Это осознанная цена за отказ от
  хранения истории по каждому клиенту.
- **Бюджет живёт в одном процессе.** Ключ HMAC случаен для каждого процесса,
  поэтому счётчики не общие между экземплярами и обнуляются при перезапуске.
  Распределённый бюджет против злоупотреблений остаётся отдельной задачей
  `content-factory-next-saas.5`.

## Публичные growth events

| Переменная | Назначение |
| --- | --- |
| `PUBLIC_GROWTH_DEDUPE_KEY` | обязательный секрет; HMAC-ключ дедупликации доверенных growth events |

Что проверяет
[public-growth.service.ts](../../libraries/nestjs-libraries/src/database/prisma/public-growth/public-growth.service.ts),
и проверяет fail-closed: длину не меньше 32 байт. Более короткое значение и
отсутствие переменной вне тестов не «деградируют до обычного хеша», а
прекращают запись доверенного receipt ошибкой. Значения в сообщении об ошибке
нет.

Что обязан обеспечить оператор, потому что код этого не увидит:

- **уникальность.** Ключ не должен совпадать с `JWT_SECRET` или любым другим
  секретом инстанса;
- **стабильность.** Ключ участвует в вычислении ключа дедупликации, поэтому
  замена ломает дедупликацию для всех receipts, которым ещё не исполнилось
  90 дней: события того же перехода после смены посчитаются заново. Плановая
  ротация — отдельный переход, а не рядовая операция.

В шаблонах [.env.example](../../.env.example) и
[app.env.example](../../deploy/production/app.env.example) переменная лежит
пустой намеренно: предсказуемое значение по умолчанию было бы хуже отсутствия.

## Переменные операторских задач

Это не переменные сервиса. Их место — строка запуска конкретной задачи, и в
`.env`/`app.env` их быть не должно:

| Переменная | Где задаётся | Назначение |
| --- | --- | --- |
| `CF_CONFIRM_SAAS_RETENTION` | unit-файл задачи, `deploy/production/retention/` | значение `apply` подтверждает намерение удалять |
| `CF_SAAS_RETENTION_TARGET` | там же — unit-файл задачи, либо строка ручного вызова | ожидаемая цель в форме `host:port/database`; скрипт сверяет её с `DATABASE_URL` и отказывается до открытия соединения при расхождении |

`CF_SAAS_RETENTION_TARGET` рядом с `DATABASE_URL` в `app.env` бесполезен:
правка, переносящая инстанс на другую базу, перенесёт и ожидаемую цель, сверка
снова сойдётся, и барьер пропустит удаление на чужой базе. Порядок и
readback — в [SaaS readiness](saas-readiness.md).

## Доставка почты

**Выключатель — `EMAIL_PROVIDER`, и только он.** `EmailService` выбирает
реализацию по его значению: `resend`, `nodemailer`, а на любом другом значении
и на пустом — `EmptyProvider`, который принимает вызов и не отправляет ничего.
Раньше здесь был описан один `RESEND_API_KEY`, и это вводило в заблуждение:
сам по себе он не включает ничего, потому что до провайдера дело не доходит.

| Провайдер | `EMAIL_PROVIDER` | Что ещё обязательно |
| --- | --- | --- |
| Resend | `resend` | `RESEND_API_KEY` |
| SMTP | `nodemailer` | `EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_SECURE`, `EMAIL_USER`, `EMAIL_PASS` |
| выключено | пусто или что угодно ещё | — |

Сверх провайдера обязательны `EMAIL_FROM_ADDRESS` и `EMAIL_FROM_NAME`. Их
проверяет не провайдер, а сам сервис, и при отсутствии любого из двух он
пишет строку в журнал и выходит — письма не будет даже при исправном
провайдере.

Транспорт `nodemailer` собирается при импорте модуля, поэтому изменение любой
из его переменных требует перезапуска приложения, а не только сохранения файла.

**Половина настройки хуже её отсутствия.** `EMAIL_PROVIDER` без рабочего ключа —
не «почти готово», а работающая блокировка регистрации.
`EmailService.hasProvider()` возвращает `true`, как только провайдер выбран, а
`auth.controller.ts` по этому же признаку решает, требовать ли активацию по
письму: `activationRequired = body.provider === 'LOCAL' && hasProvider()`.
То есть новый аккаунт получит ответ «подтвердите адрес», а письмо не придёт,
потому что ключ нерабочий, — и войти будет нельзя вообще. Пока провайдер не
выбран, регистрация просто работает без активации. Поэтому `EMAIL_PROVIDER` и
ключ выставляются **одной операцией**; ровно так это делает
`scripts/operations/set-email-provider.sh`.

### Что именно ломается без почты

Это не «уведомления не приходят». Отсутствие провайдера выключает поведение,
которое выглядит рабочим:

- **Добавить вход по паролю нельзя вообще.** Адрес становится способом входа
  только после перехода по ссылке из письма; без письма ссылки не существует.
- **Сброс пароля молча ничего не делает.** Форма отвечает так же, как при
  успехе — она намеренно не раскрывает, есть ли такой аккаунт.
- **Активация аккаунта** по ссылке из письма недоступна.

Поэтому на развёртывании, где выдан вход по паролю, почта не опция.

### Один SMTP на продукт и рассылку

Listmonk отправляет письма подтверждения подписки сам и требует собственных
настроек SMTP в своей админке — они не читаются из `app.env`. Если выбирать
между Resend и SMTP только ради продукта, разницы почти нет; но одна учётная
запись SMTP закрывает и продукт, и рассылку, а Resend придётся заводить в
Listmonk отдельно через его SMTP-эндпоинт. Порядок для рассылки —
[newsletter.md](newsletter.md).

## Одобрение аккаунтов

`DISABLE_REGISTRATION="true"` закрывает форму регистрации целиком. `CONTENT_FACTORY_REQUIRE_APPROVAL="true"` решает другую задачу: форма остаётся открытой, но созданный аккаунт до одобрения не может ничего — API отказывает ему на каждом запросе, потому что middleware перечитывает пользователя из базы, а не верит токену.

Что меняется при включённом режиме:

- новый аккаунт создаётся с `activated=false` независимо от способа входа, включая Google, GitHub и Telegram: провайдер подтверждает, кто человек, а не то, что инстанс его ждёт;
- при регистрации не выдаётся cookie сессии и не отправляется письмо с ссылкой активации — ссылка в таком письме и есть тот самый доступ, который должен выдавать администратор;
- `/auth/activate/:code` и повторная отправка письма отвечают отказом;
- вход в неодобренный аккаунт отвечает `User is awaiting approval`, и страница входа объясняет, что ждать нужно человека, а не письма.

Первый аккаунт на пустом инстансе исключением больше не является: он создаётся так же, как любой другой, и прав администратора не получает. Раньше их выдавали по отсутствию организаций в базе, но на инстансе с публичной регистрацией первым зарегистрируется не владелец. Одобрять поэтому будет некому, пока оператор не создаст администратора сам — порядок в [Bootstrap администратора инстанса](production-deploy.md#bootstrap-администратора-инстанса), и он выполняется до открытия публичного трафика.

Одобряет и блокирует администратор на странице `/admin/users`: вкладки «ожидают / активные / все», поиск по почте и имени, кнопки одобрения и блокировки. Блокировка вступает в силу со следующего запроса и обрывает уже открытую сессию. Аккаунт с правами администратора заблокировать нельзя — это единственный способ остаться без администраторов вообще.

Один и тот же признак `activated` описывает и ожидание одобрения, и блокировку. Заблокированному человеку страница входа скажет, что аккаунт ожидает одобрения; администратор видит разницу по истории действий, а не по интерфейсу.

Cookie сессии выдаётся на точный хост из `FRONTEND_URL`. Раньше область расширялась до регистрируемого домена, и инстанс на `factory.example.com` отдавал свою сессию всем соседним поддоменам `example.com`. Если одна сессия действительно должна охватывать несколько поддоменов, это заявляется явно через `AUTH_COOKIE_DOMAIN`.

Включённый `CONTENT_FACTORY_GENERIC_OAUTH="true"` заменяет собой все остальные кнопки входа — Google, GitHub и Telegram на странице входа не появятся. Не задавайте переменную, если self-hosted provider не настроен.

Развёрнутый инстанс, адреса и порядок обновления описаны в [Развёртывании на сервере](production-deploy.md).

## Хранилище

`STORAGE_PROVIDER=local` использует `UPLOAD_DIRECTORY` и публичный upload path. Cloudflare R2 использует `CLOUDFLARE_*`. Эти credentials секретны. Volume/директория должны переживать перезапуск контейнера.

Перед сменой provider нужен план переноса уже сохраненных `Media.path`; изменение одной env variable не переносит файлы.

## Социальные платформы

Каждая OAuth-платформа имеет client id/secret или token variables в `.env.example`: X, LinkedIn, Reddit, Threads/Facebook/Instagram, YouTube, TikTok, Pinterest, Dribbble, Tumblr, Discord, Slack и другие. Некоторые self-hosted providers принимают URL/credentials на уровне подключения канала.

Правила:

- не коммитить реальные значения;
- redirect URI регистрировать для точного внешнего origin;
- scopes держать минимальными;
- credentials разных сред не смешивать;
- проверять требования provider implementation и его `scopes`;
- `DISABLE_SSRF_PROTECTION=true` допустим только в доверенной частной сети после отдельной оценки риска.

## AI и сторонние сервисы

- По умолчанию существующие настройки работают в режиме `workspace_key`: ключи
  OpenAI/OpenRouter и Tavily вводятся администратором организации, шифруются в
  `AiProviderSetting` и никогда не возвращаются в браузер.
- Новая организация атомарно получает `AiProviderSetting` с режимом
  `included`. Пока месячная квота равна нулю или управляемый ключ отсутствует,
  API возвращает безопасное ограниченное состояние без обещания автоматического
  пополнения. Администратор может явно выбрать `workspace_key`.
- Режим `included` читает только `AI_INCLUDED_API_KEY` и
  `AI_INCLUDED_SEARCH_API_KEY`. Он не использует сохранённый ключ организации
  как запасной и закрыт, если управляемого ключа или месячной квоты нет.
- `AI_PROVIDER`, `AI_BASE_URL`, `AI_TEXT_MODEL` и `AI_IMAGE_MODEL` задают
  provider и модели для `included`; это не секреты. Смена режима применяется к
  следующей операции без process-local TTL.
- `.env.example` не использует `OPENAI_API_KEY`, `OPENROUTER_API_KEY` или
  `TAVILY_API_KEY`: runtime не читает их как запасные credentials. Ключи
  `workspace_key` вводятся в настройках организации, а server-managed режим
  читает только две переменные `AI_INCLUDED_*` выше.
- `Subscription.includedAiMonthlyOperations` пока имеет безопасный предел `0`.
  Ненулевые значения относятся к отдельному решению о тарифах и здесь не
  назначаются.
- Отказы AI приходят с полем `code`; их перечень и разница между «квота
  кончилась» и «журнал допуска занят» — в
  [Эксплуатации](runtime.md#коды-ошибок-ai).
- short-link providers используют отдельные token/domain variables;
- Stripe и Resend имеют собственные секреты и webhook signing keys;
- `NEXT_PUBLIC_SUPPORT_URL` — адрес канала поддержки, куда ведёт кнопка в
  интерфейсе. Переменная не задана, поэтому кнопки нет: это осознанное
  состояние, пока у продукта не появится собственный канал. Прежнее имя
  `NEXT_PUBLIC_DISCORD_SUPPORT` вело в Discord апстрима и удалено;
- аналитики, рекламных счётчиков и встроенного редактора изображений в инстансе
  нет: соответствующие пакеты и переменные удалены из дерева, а не отключены;
- ошибки уходят только в свой GlitchTip и только при совпадении DSN с отдельно
  заданным точным origin. Сам [сборщик](error-collection.md) поставляется
  отдельным стеком, не зависит от приложения и хранит события и файлы 30 дней.
  Browser напрямую ошибки не отправляет: даже очищенный payload раскрыл бы
  collector и reverse proxy пользовательские IP и User-Agent.

### Сбор ошибок

| Переменные                     | Назначение                                                                     |
| ------------------------------ | ------------------------------------------------------------------------------ |
| `CONTENT_FACTORY_ERROR_DSN`    | ingest DSN собственного GlitchTip для backend, orchestrator и Next server/edge |
| `CONTENT_FACTORY_ERROR_ORIGIN` | отдельно заданный точный origin собственного GlitchTip                         |
| `CONTENT_FACTORY_RELEASE`      | commit SHA образа для сопоставления ошибки с версией                           |

Группа необязательна. DSN и origin должны иметь одинаковые
scheme, host и port; origin не может содержать path, query, credentials или
fragment. Одного DSN недостаточно, поэтому случайная переменная не направит
события во внешний SaaS. Release лучше задавать commit SHA образа.

Платные AI-вызовы и внешние записи в рамках разработки выключены по умолчанию и требуют явного разрешения.

## Документация API

`CONTENT_FACTORY_SWAGGER_ENABLED="true"` публикует Swagger. По умолчанию переменная не задана, и документации нет. Включает только точная строка `true`; отдельная переменная выбрана намеренно — привязка к `NODE_ENV` или к любому уже занятому переключателю означала бы, что два несвязанных поведения делят одно решение.

Один вызов регистрирует три пути, а не один:

| Путь бэкенда | Снаружи, через nginx | Что отдаёт                 |
| ------------ | -------------------- | -------------------------- |
| `/docs`      | `/api/docs`          | интерфейс Swagger UI       |
| `/docs-json` | `/api/docs-json`     | спецификация OpenAPI, JSON |
| `/docs-yaml` | `/api/docs-yaml`     | та же спецификация, YAML   |

Снаружи они доступны по `/api/...`: nginx проксирует на бэкенд только `location /api/`, корень домена уходит на фронтенд. Аутентификации у этих путей нет — маршруты регистрируются напрямую в Express, мимо guard'ов Nest.

В документ попадает полный перечень маршрутов бэкенда, включая admin, oauth и enterprise. Тела запросов и ответов в него не попадают: в дереве нет ни одного декоратора `@ApiProperty`, а плагин `@nestjs/swagger` в [nest-cli.json](../../apps/backend/nest-cli.json) отключён (`"plugins": []`). То есть это карта путей, а не описание модели данных, — поэтому вопрос и остаётся некритичным. Но отсутствие схем не является причиной публиковать сами пути: на инстансе с одним пользователем и без внешних потребителей API документация не даёт ничего, а читателю выдаёт готовый список точек входа.

Включайте на время работы над интеграцией и снимайте после. Поведение закреплено в `tests/swagger.gate.test.cjs`: тест поднимает настоящее приложение Nest и проверяет все три пути в обоих состояниях переменной.

## Добавление переменной

1. Выберите server-only или `NEXT_PUBLIC_` осознанно: публичная переменная попадает в browser bundle.
2. Добавьте безопасный placeholder и комментарий в `.env.example`.
3. Добавьте runtime validation/default в существующий config path.
4. Обновите этот документ, если переменная обязательна, чувствительна или меняет инфраструктуру.
5. Не добавляйте fallback, который выглядит как production secret.
