# Telegram adaptation chain repair

Task: `content-factory-next-5rgn`. Owner explicitly requests repair of the whole
chain, restoration of their avatar/removal of QA settings, two actual reruns,
display of resulting posts, and preservation of original versions.

## Accepted outcome and design

Research stays structured from the owned research snapshot into intake and the
piece: each chosen statement retains its actual source URL, supporting quote
and durable evidence identity. A repeated fetch is not required to recover
already collected evidence. Original request/reference roles stay distinct.
Adaptation changes presentation while retaining requested coverage; evidence
outside the first 800 page characters must remain usable. No source ID alone
certifies arbitrary text. The finished, saved adaptation is read and assessed
against the original task before reporting completion. Use the existing product
services, native chat and model routes, without a parallel writer.

Current diagnosis: original cores are 2391/2858 characters; adaptations are
294/460. Both generation snapshots have one API-changelog evidence prefix of
800 characters, with a source-only factual rule conflicting with core
preservation. Both applied a QA voice from channel preferences. Private originals
and read-only proof: `/tmp/cf-adaptation-audit-20261020`; public-safe prior audit
is in the starting checkout's stage directory.

## Cohesive ownership and scope ledger

1. Research provenance -> source stream: capability research reuse, intake
   contract/state and source persistence, focused regression tests.
2. Adaptation completeness -> generator stream: consistent source/core rules,
   supported claim spans and complete opening/body persistence, bounded
   semantic quality verification/repair where needed, focused regressions.
3. Saved-result verification, configuration recovery, integration and delivery
   -> root: adaptation tool/model output and conductor instructions, actual
   saved-body inspection, owner-selected avatar and removal of QA preferences,
   release verification and the two natural request reruns.
4. Original versions -> root: private baseline and post-run comparison of exact
   original thread messages, pieces, adaptations and posts. Reruns create new
   conversations/artifacts and cannot schedule or publish social posts.

Workers share one isolated worktree but disjoint write zones. Each is told not
to revert concurrent edits. Root records delivered/accepted results and resources.

## Risks and recovery (technical premortem)

| Symptom | Mechanism | Check / mitigation |
| --- | --- | --- |
| Unsupported claim gains confirmation | Reused text assigned an arbitrary evidence ID | Keep source/quote pairing; validate owned snapshots and exact support references; regression with mismatched ID |
| Digest loses topics | Prefix-only source constraint or QA truncation | Multi-source and beyond-offset-800 tests; actual saved posts inspected |
| Review adds cost/loops | Repair retries every draft | Bounded attempts, accounted existing role, no recursive unbounded rewriting |
| Old variants overwritten | Retry calls edit instead of create | New conversations/new variants; compare baseline hashes |
| Posts published during QA | Channel plan mode autopilot | Preserve safe reserve/draft mode; no publish/schedule consent |
| Other owner data/config lost | Broad cleanup or stale channel patch | Scope one organization/channel, backup and compare-and-set; retain originals |
| Executor claims fixture quality | Green tests mistaken for publication quality | Separate offline wiring, live execution, and editorial reading |

No schema migration is planned. Existing live image remains the code rollback;
channel configuration gets a private before/after record and scoped restoration.
No secrets or private original texts enter Git/public tree. Current user request
authorizes necessary product correction and paid reruns; no social publication.
