# Выбор web-search backend для русскоязычного Telegram-пайплайна

## Рекомендация

**Primary — OpenRouter `web` plugin, жёстко зафиксированный на `engine: "parallel", mode: "advanced"`; не использовать голый `:online` как production-default.** Он выигрывает по совокупности критериев, потому что Parallel прямо заявляет покрытие русскоязычного контента, принимает запросы на любом языке, возвращает LLM-ready excerpts, а через OpenRouter Advanced стоит $5 за 1 000 поисков и оплачивается из уже существующего OpenRouter-баланса каждого workspace; важная оговорка — опубликованный Parallel multilingual benchmark является **vendor-run**, а не независимым тестом русского поиска ([Parallel, 21.04.2026](https://parallel.ai/blog/parallel-search-api); [OpenRouter Web Search, дата на странице не указана, проверено 13.08.2026](https://openrouter.ai/docs/guides/features/plugins/web-search)). citeturn24view0turn23search1 Naked `:online` хуже именно как инфраструктурное решение: OpenRouter выбирает provider-native search для части моделей и Exa для остальных, тогда как явный `engine:"parallel"` делает retrieval-поведение, цену и русскоязычную гипотезу воспроизводимыми при смене LLM ([OpenRouter Web Search, без даты, проверено 13.08.2026](https://openrouter.ai/docs/guides/features/plugins/web-search)). citeturn23search1 **Primary проигрывает**, если ваш собственный русский benchmark покажет существенно худший recall российских медиа, чем Yandex/SerpAPI-Yandex, либо юрист/Parallel подтвердит, что ограничение «один Customer Output — преимущественно для одного End Customer» несовместимо с вашей схемой последующей массовой публикации в Telegram ([Parallel Customer Terms, 01.07.2026](https://parallel.ai/customer-terms)). citeturn29view0

**Fallback — Tavily `advanced` с `include_raw_content`, сохранив уже существующую интеграцию.** Tavily выигрывает роль fallback, а не primary: он уже встроен в ваш LangGraph-стек, умеет вернуть cleaned/parsed page content в Markdown/text и имеет гораздо более явные временные фильтры — `time_range`, `start_date`, `end_date` — поэтому при сбое или деградации OpenRouter/Parallel не требуется строить новый extraction path ([Tavily Search, 09.02.2025](https://docs.tavily.com/documentation/api-reference/endpoint/search); [LangChain Tavily integration, дата страницы не указана, проверено 13.08.2026]). citeturn21search7turn1search11 При PAYG advanced-search расходует два кредита, то есть $0.016 за поиск при $0.008/credit, а официальный changelog подтверждает продолжающееся развитие режимов поиска; заявленные 99.99% SLA/latency следует считать **vendor marketing**, а не независимой проверкой ([Tavily Pricing, без даты, проверено 13.08.2026](https://docs.tavily.com/documentation/api-credits); [Tavily changelog, декабрь 2025](https://docs.tavily.com/documentation/changelog)). citeturn2search0turn2search7turn2search5 **Fallback проигрывает Yandex/SerpAPI-Yandex**, когда причиной переключения является именно плохой recall русскоязычных источников: в изученной публичной документации Tavily я не нашёл официального русского language mode, российского index-coverage statement или отдельного русского benchmark, поэтому его RU-качество остаётся существенно менее доказанным, чем у Parallel, Perplexity и Yandex. citeturn21search7turn21search4

*Предположение, которое влияет на вывод: один research-node делает в среднем три логических веб-поиска на пост — discovery, freshness и cross-check — после чего единый research-result повторно используется четырьмя downstream prompts; оценка цены ниже построена именно на трёх поисках, а не на четырёх генерационных стадиях.*

Весовая модель для решения: **русский поиск 30%**, ToS/коммерческое использование 18%, output shape 14%, multi-tenant/billing 10%, стоимость 9%, recency 8%, reliability 7%, integration 4%. Баллы — от 1 до 5; итог — взвешенная аналитическая оценка, а не опубликованный vendor score.

## Русскоязычный поиск

Главная находка исследования состоит не в том, что какой-то API доказал превосходство на русском, а в том, что **публичная доказательная база очень слабая**. Я не нашёл независимого contemporary benchmark, где Tavily, Parallel, Brave, Exa, Perplexity, Serper/Google, SerpAPI/Yandex и Yandex native были бы прогнаны на одном и том же наборе русских news-запросов с оценкой recall/precision, freshness и долей российских доменов. Поэтому англоязычные SimpleQA, BrowseComp, HLE, FRAMES и аналогичные цифры не должны решать этот выбор; они максимум проверяют общую зрелость retrieval.

**Самое сильное прямое свидетельство среди AI-native search layers сейчас у Parallel.** В релизе от **21 апреля 2026 года** Parallel отдельно пишет, что его index охватывает страницы из 30+ стран, явно перечисляя **Russian-language content**, и что API принимает query input «in any language» без отдельной настройки. citeturn24view0 Это больше, чем абстрактная фраза “multilingual”: поставщик сделал multilingual evaluation на 26 языках, взяв по 100 вопросов на язык и сравнивая падение accuracy относительно английского; вопросы подавались провайдерам «as-is», а ответы оценивались одним LLM judge. citeturn24view0 Но это всё ещё **Parallel benchmark of Parallel**: поставщик выбрал harness, dataset и judge, а опубликованный текст не даёт отдельной цифры именно по русскому, поэтому доказательство получает высокий, но не максимальный вес. citeturn24view0

Для вашего конкретного pipeline у Parallel есть ещё одна важная особенность: direct Search API принимает массив `search_queries`, причём документация рекомендует 2–3 коротких query на один research objective, и возвращает ranked, compressed excerpts, предназначенные непосредственно для model context. citeturn23search2turn23search7 Это практически совпадает с вашей архитектурой: research-node может искать, например, «новость/событие», «свежее подтверждение», «альтернативный источник», после чего положить один компактный research artifact в LangGraph state и больше не платить за веб retrieval на стадиях hook/body/image prompt. Через OpenRouter, однако, multi-query semantics direct Parallel API не документированы как часть общего web-plugin interface, поэтому в cost model ниже я консервативно считаю три платных search calls, а не один. citeturn23search4

**Yandex — наиболее сильный кандидат именно на оси “Russian web”, но не наиболее сильный backend для всей задачи.** Официальный Yandex Search API имеет `SEARCH_TYPE_RU`, то есть разработчик может ограничить retrieval русскоязычным сегментом интернета. citeturn14search1 Независимый StatCounter за **июль 2026 года** оценивал долю Yandex среди поисковиков в Российской Федерации примерно в 72.85%, против примерно 25.48% у Google; это полезное подтверждение локальной значимости индекса, но нельзя превращать market share в доказательство лучшего API recall. citeturn13search9 Именно поэтому Yandex включён как дополнительный кандидат, который материально превосходит большинство списка по доказанной ориентации на русский сегмент, но не как primary: стандартный Search API не решает вашу задачу extraction/LLM-ready corpus, а commercial downstream licensing в текущем исследовании остался не верифицирован. citeturn14search0turn31search0

**SerpAPI становится интересен на русском не потому, что SerpAPI имеет собственный лучший индекс, а потому, что официально экспонирует Yandex как engine.** Для Yandex endpoint документированы `lang=ru`, `yandex_domain=yandex.ru` и time-oriented sorting/period controls; одновременно SerpAPI умеет Google с `hl`/`gl` локализацией. citeturn6search1turn6search9turn6search13 Это делает его, вероятно, самым удобным способом провести будущий Yandex-vs-Google benchmark через один schema/API, но production-выигрыш слабее: за довольно высокую цену вы всё равно получаете прежде всего SERP JSON, после которого понадобится fetch/extract layer.

**Perplexity имеет наиболее чёткое “официально поддерживается русский” свидетельство после Yandex/Parallel:** его search filter принимает ISO-639-1 и прямо включает `"ru"`. citeturn19search1 Но фильтр доказывает возможность запросить русские источники, а не качество ранжирования российской новостной выдачи; независимого RU-specific Sonar retrieval benchmark я не нашёл. Дополнительный минус на дату решения — **16 июля 2026 года** Perplexity обновил документацию так, что Sonar назван legacy и новым интеграциям рекомендуют Agent API. citeturn19search8

**Exa имеет более содержательную multilingual evidence, чем Tavily или Brave, но она недостаточна для первого места.** На продуктовой странице Exa публикует результаты на MultiLoKo и заявляет, например, для своих режимов существенно более высокий aggregate accuracy, чем Brave/Perplexity/Parallel; это **vendor-run benchmark**. citeturn22search0 Сам MultiLoKo — опубликованный в 2025 году академический multilingual local-knowledge benchmark на 31 языке, то есть он значительно релевантнее English-only SimpleQA, но Exa не публикует на рассматриваемой странице отдельную Russian slice. citeturn21search0turn21search9 Поэтому я считаю это слабым положительным сигналом, а не доказательством лучшего русского поиска.

**Tavily — самая большая неопределённость относительно incumbent.** Его product shape для вашего LangGraph отличный: Search может вернуть clean/raw content, news mode и временные ограничения, а публичные evals демонстрируют хорошую общую retrieval performance. citeturn21search7turn21search27 Но просмотренные официальные материалы не дали сопоставимого с Parallel заявления о Russian index coverage, сопоставимого с Perplexity `ru` filter или сопоставимого с Yandex `SEARCH_TYPE_RU`; поэтому сделать incumbent primary означало бы фактически дать интеграционному удобству больший вес, чем пользователем заданному критерию №1.

**Serper — разумная “Google baseline”, а не AI-research backend.** Serper утверждает, что обращается к Google в real time, поддерживает language/country customization и не отдаёт кэшированные SERP; эти сведения исходят от самого Serper. citeturn4search0 Для русского это означает полезный контрольный канал против Yandex/Parallel, но без отдельной RU quality measurement и без full-text extraction он не обгоняет primary по вашей архитектуре.

**Brave следует оценивать отдельно по retrieval и по contract fit.** С технической стороны февральский релиз 2026 года очень хорошо попадает в вашу задачу: LLM Context превращает результаты в ranked smart chunks из страниц и продаётся в том же Search plan за $5/1k. citeturn21search17 Но результат их own evaluation, где Brave-backed Ask Brave превосходит конкурентов, является **vendor marketing/vendor-run evaluation**; прямого русского slice нет. citeturn21search17 Ещё важнее, public ToS делает contractual risk настолько высоким, что retrieval quality перестаёт быть решающим. citeturn29view3

**SearXNG не создаёт нового русского индекса — он оркестрирует чужие.** В документации версии **2026.7.28** есть `language`, locale и `time_range`; сам query пересылается external search services, а JSON/RSS/CSV являются нормализованной выдачей поверх upstream engines. citeturn30search0turn30search4 Теоретически это даёт максимальную свободу объединить Yandex/Google/Brave/другие engines, но одновременно переносит на вас все проблемы блокировок, изменений HTML/API, legal terms и мониторинга; найденный GitHub report о CAPTCHA у Yandex относится ещё к 2022 году и потому используется лишь как историческое предупреждение, не как описание состояния 2026 года. citeturn13search5

**Telegram и VK — критический пробел у всех кандидатов.** Ни в одной из проверенных публичных спецификаций я не нашёл contractual/technical guarantee, что Telegram channels или VK posts индексируются полно, быстро и с recoverable body text; поэтому нельзя начислять ни Parallel, ни Yandex, ни Google-посредникам «баллы за Telegram/VK» на основании общего web coverage. Это особенно важно потому, что позже у вас появятся RSS и Telegram donor channels: **Telegram donor ingestion лучше рассматривать как отдельный first-party source layer, а web search — как corroboration/discovery layer**, а не надеяться, что поисковый индекс заменит прямое получение donor content.

Практический русский benchmark, который способен снять основную неопределённость, должен быть небольшим, но локальным: порядка 150–300 запросов, разделённых на breaking news, федеральные/региональные СМИ, отраслевые медиа, long-tail русские сайты и запросы, где известен Telegram/VK origin. Метрики, которые действительно относятся к вашей задаче, — доля top-5 с русскоязычным primary source, recall заранее известного источника, median source age, duplicate-domain rate, количество usable extracted characters и factual sufficiency результата для написания поста; английские QA accuracy benchmarks этим требованиям не эквивалентны.

## Условия коммерческого использования

Это сравнительный contractual-risk review, не юридическое заключение. Для вашего use case вопрос не сводится к «можно ли вызвать API коммерчески»: нужно, чтобы результат можно было **временно хранить в LangGraph state, переработать LLM в производное произведение и затем опубликовать это произведение публично и коммерчески**.

**OpenRouter + Parallel.** OpenRouter Terms, обновлённые **29 июля 2026 года**, прямо говорят, что права на Output зависят от применимых provider/model terms и что пользователь должен учитывать условия third-party services. citeturn27search0turn29view2 Parallel Customer Terms от **1 июля 2026 года** значительно яснее большинства search vendors: `Customer Output` входит в `Customer IP`, а клиент может «modify, adapt, or create derivative works» и включать их в материалы для End Customers. citeturn29view0 Но там же есть необычное ограничение: output одного query должен быть primarily for use of one End Customer и не должен превращаться в cross-customer cache/data-selling service. citeturn29view0 Для вашей tenancy-модели это **может** хорошо ложиться на схему «один workspace = один customer, research result не разделяется между tenants», но публичная публикация производного Telegram-поста множеству читателей заслуживает письменного подтверждения Parallel/OpenRouter; я не стал трактовать contract шире его текста.

**Tavily.** Tavily Platform Terms имеют дату **4 мая 2026 года** и возлагают на клиента ответственность за third-party services/content и проверку output. citeturn2search9 В просмотренной публичной версии я не нашёл настолько же явного grant, как у Parallel, разрешающего derivative publication of search-derived material; одновременно не найден и Brave/Exa-подобный прямой запрет. Поэтому verdict — **usable with ordinary copyright/factual-summary discipline, но commercial-reuse license публичными terms доказана не полностью**.

**Brave.** Terms от **11 февраля 2026 года** разрешают использовать Search Results внутри Customer Applications, но запрещают хранить/cache их кроме transient operational storage, запрещают создавать derivative works of Search Results и запрещают redistributing/reselling Search Results. citeturn31view3turn29view3 Для architecture, где fetched chunks намеренно становятся источником текста коммерческого Telegram-поста, это не та двусмысленность, которую стоит «сгладить»: **до письменного разъяснения Brave я бы не ставил этот backend в production**, даже если LLM Context технически очень хорош. Attribution `POWERED BY BRAVE` в terms сформулирован как допустимый/регулируемый вариант, но attribution не снимает derivative-work restriction. citeturn31view3

**Serper.dev.** Terms, обновлённые **29 мая 2024 года**, указывают, что data может содержать third-party content/IP и что пользователь не должен использовать такой материал без лицензии либо иного разрешения закона. citeturn4search1 Я не нашёл прямого запрета на коммерческий factual synthesis или временный cache, но также не нашёл affirmative license на republishing source material. Поэтому безопасное использование — извлекать факты, сохранять attribution/citations и не копировать substantial expression источника.

**SerpAPI.** Legal Terms обновлены **8 апреля 2026 года**, запрещают unlawful/copyright-infringing use и предоставляют 99.95% SLA, но не превращают данные поисковиков в контент, который SerpAPI может лицензировать вам как свой. citeturn31view2 Отдельное объяснение SerpAPI от **29 апреля 2024 года** подчёркивает важную границу: их U.S. Legal Shield касается законности scraping/parsing, **не downstream use данных**. citeturn5search2 Поэтому SerpAPI снимает часть scraper risk, но не вопрос авторских прав к российским статьям, попавшим в SERP.

**Exa direct.** Это второй после Brave серьёзный red flag. В публичном PDF Exa Terms, на котором я не обнаружил даты, clause 4.2 запрещает без письменного разрешения, среди прочего, публиковать, распространять или создавать derivative works из информации, полученной through the Services; третьесторонние материалы рассматриваются отдельно. citeturn11view1turn12view0turn12view1 Из-за широкой формулировки я не рекомендую direct Exa для коммерческого Telegram synthesis до получения письменного carve-out/MSA, хотя технически Exa один из лучших вариантов.

**Perplexity Sonar.** Здесь результат исследования намеренно остаётся **unverified**: официальный URL API Terms найден, но его содержимое не удалось получить через доступный reader в этом проходе. citeturn31view0 Вторичные страницы цитируют API Terms как отдельный договор и утверждают права клиента на output, но по заданному вами правилу vendor/secondary hearsay недостаточно для contractual decision, поэтому я не засчитываю это как подтверждённое разрешение. citeturn28search2turn28search0

**SearXNG.** AGPL-3.0 регулирует сам software, а не права на third-party search results. citeturn13search1 Поскольку SearXNG прямо передаёт запросы external search services, self-hosting не отменяет ToS и content/IP restrictions соответствующих engines; это архитектурный вывод из документации, а не отдельная лицензия SearXNG. citeturn30search0 То есть «self-hosted» решает key/vendor-control problem, но не делает Google/Yandex content юридически вашим.

**Yandex Search API.** Я подтвердил официальный API и его pricing/quotas, но не смог в этом проходе получить публичный contractual text, который однозначно отвечает именно на вопрос «может ли SaaS использовать результаты для генерации массово публикуемого коммерческого текста». citeturn31search0turn17search2 Поэтому Yandex не получает презумпцию разрешения: этот пункт остаётся **обязательной legal verification перед production**, и именно он мешает сделать Yandex fallback несмотря на 5/5 по русской оси.

Иными словами, технически привлекательные **Brave и Exa direct падают из-за явно рестриктивного публичного текста**, Perplexity и Yandex падают из-за неполной проверки contract evidence, а OpenRouter+Parallel остаётся впереди потому, что Parallel хотя бы прямо выдаёт клиенту права на modification/derivative output при известных ограничениях. citeturn29view0turn29view3turn11view1

**Базовое допущение: три логических поиска на один опубликованный пост.** Это не четыре search calls по числу downstream prompts: research выполняется один раз, сохраняется в LangGraph state, а topic selection, hook, body и image prompt читают тот же результат. Модельная генерация downstream не включена; для OpenRouter/Perplexity отдельно отмечены дополнительные token costs, поскольку без выбранной LLM и среднего context size их нельзя честно превратить в фиксированную цифру.

Есть важная экономическая деталь: **стоимость самого поиска здесь почти нигде не является решающей**. Это и объясняет, почему Serper при номинальных ~$3/1 000 posts не выигрывает: его links/snippets заставляют строить и эксплуатировать extraction layer, который Parallel/Tavily/Brave Context/Exa уже частично закрывают. citeturn23search2turn21search7turn21search17turn22search0

То же касается Yandex: ₽1,464 на тысячу постов выглядит очень конкурентно для native Russian retrieval, но затем нужно самостоятельно fetch → boilerplate removal → article extraction → truncation/reranking. citeturn31search0turn14search0 Поэтому Yandex наиболее интересен как **русский recall oracle / benchmark comparator**, а не как первый production backend при нынешней архитектуре.

## Непроверенные заявления и пробелы

- **Нет независимого head-to-head русского benchmark.** Ни один найденный источник не сравнивает все кандидаты на одном contemporary наборе русскоязычных media queries. Parallel multilingual test, Exa MultiLoKo numbers, Tavily SimpleQA/SealQA и Brave LLM Context evaluation либо vendor-run, либо не дают Russian-only slice. citeturn24view0turn22search0turn21search27turn21search17

- **Telegram/VK coverage не подтверждён ни для одного backend.** Нельзя на основании общего “web index” утверждать, что конкретный API полно и своевременно индексирует Telegram channels или VK posts; найденные public docs такой гарантии не дают.

- **Tavily Russian quality — unverified.** Нет найденного официального `ru` filter, Russian index-coverage statement или Russian benchmark; отсутствие такого evidence — одна из основных причин, почему incumbent не primary. citeturn21search7turn21search4

- **Parallel Russian benchmark — частично проверен.** Подтверждены Russian-language index coverage, multilingual queries и methodology на 26 языках, но отдельная цифра accuracy/recall по русскому в доступном тексте не опубликована; поэтому claim «Parallel лучший на русском» был бы сильнее данных. citeturn24view0

- **Parallel через OpenRouter и direct Parallel terms.** OpenRouter прямо требует учитывать third-party terms, а Parallel public customer terms разрешают derivatives с one-End-Customer limitation; я не нашёл отдельного публичного соглашения, которое явно говорит, что OpenRouter web-plugin customers получают идентичную лицензию на Parallel output. citeturn29view2turn29view0

- **Perplexity API commercial-output rights не засчитаны как verified.** Официальная API Terms page не распарсилась в этом research run; secondary statements существуют, но по вашим правилам их недостаточно. citeturn31view0turn28search0

- **Yandex commercial publication terms не верифицированы.** Технические docs, цена и квоты проверены, но contractual grant на превращение search results в публичный коммерческий Telegram content — нет. citeturn31search0turn17search2

- **Brave Russian quality не доказана.** Подтверждены independent index и LLM Context, но не найден Russian-only quality test; собственные head-to-head Brave нельзя считать независимыми. citeturn21search17turn21search2

- **Exa MultiLoKo не равен “Exa хорошо ищет российские СМИ”.** MultiLoKo — хороший multilingual signal, но опубликованные Exa numbers агрегированы и vendor-run; это не измерение Russian news recall. citeturn22search0turn21search9

- **Serper “Google real-time/no cache”, latency и QPS — vendor claims.** Я не нашёл независимой текущей measurement series, которая подтверждала бы эти характеристики при scheduled production load. citeturn4search0

- **Tavily 99.99% SLA / latency figures — vendor-only evidence в найденном материале.** Их нельзя смешивать с SerpAPI 99.95% SLA, который прямо записан в contractual Legal Terms. citeturn2search5turn31view2

- **Exa Terms PDF не содержит видимой даты в просмотренных страницах.** Именно поэтому restrictive clauses описаны как текущий публично доступный текст, прочитанный 13.08.2026, а не как Terms “от” конкретной даты. citeturn12view0turn12view1

- **SearXNG cost нельзя честно назвать нулевым.** Нулевой только внешний per-request fee; CPU/RAM, proxy/IP reputation, monitoring, upgrades, failure handling и инженерное время зависят от вашей deployment architecture и не были публично заданы. citeturn13search6turn30search0

- **Русские benchmark results могут зависеть от географии запроса.** Parallel direct API имеет location parameter, Serper/Google и SerpAPI поддерживают localization, Yandex имеет native Russian segment; OpenRouter abstraction не экспонирует одинаковый location/freshness surface для всех engines. Поэтому будущий A/B test должен фиксировать region, language и query formulation, иначе сравнение будет смешивать backend quality с конфигурацией. citeturn24view0turn4search0turn23search4

## Что изменит рекомендацию

**Решение перевернёт прежде всего русский empirical benchmark, а не очередной англоязычный leaderboard.** Если на слепом тесте из хотя бы ~200 репрезентативных русских queries — новости, regional media, niche publishers, известные-source retrieval, свежие события — **Yandex native или SerpAPI-Yandex даст примерно на 15 процентных пунктов и более лучший top-5 known-source recall либо ≥20% больше usable Russian-source coverage**, при сопоставимой freshness, я бы сменил primary на Yandex-oriented retrieval и добавил собственный extraction layer; такой порог является моим decision rule, а не опубликованным industry standard. Официальный `SEARCH_TYPE_RU` и текущая значимость Yandex дают достаточно оснований ожидать, что этот тест может изменить результат, но не достаточно оснований объявить победу до теста. citeturn14search1turn13search9

**Юридическое подтверждение также способно мгновенно изменить порядок.** Если Parallel/OpenRouter письменно подтвердят, что current Customer Output grant разрешает вашему SaaS хранить research artifact в рамках одного workspace и использовать его для коммерчески публикуемого Telegram derivative, primary станет значительно увереннее; если они скажут обратное, OpenRouter+Parallel немедленно перестаёт быть рекомендацией независимо от search quality. citeturn29view0turn29view2 Аналогично, письменный enterprise carve-out от Brave или Exa, прямо разрешающий storage + LLM-derived commercial publication, резко поднимет их позиции, потому что именно ToS, а не output quality, сейчас удерживает их вне top two. citeturn29view3turn11view1

**Tavily может вернуть себе primary без смены продукта**, если controlled RU test покажет parity с Parallel — например, разницу менее ~5 percentage points по Russian top-5 recall/factual sufficiency — поскольку тогда его уже существующая LangGraph integration, лучшие explicit date controls и проверенный `include_raw_content` устраняют смысл миграции ради недоказанного retrieval gain. citeturn21search7turn1search11 И наоборот, если Tavily заметно отстаёт на российском long-tail или breaking news, он остаётся только operational fallback независимо от удобства incumbent.

**OpenRouter может укрепить primary технически**, если его web-plugin добавит documented language/region/freshness controls для Parallel и возможность передавать несколько `search_queries` в один billed Parallel request. Сейчас direct Parallel умеет objective + 2–3 search queries и freshness policy, тогда как generic OpenRouter surface предоставляет более ограниченный унифицированный набор controls; устранение этого gap сделает consolidation не только удобным, но и почти без компромисса по retrieval control. citeturn23search2turn23search5turn23search4

**Perplexity может войти в top two**, если одновременно произойдут две вещи: будет верифицирован API contract с явным commercial derivative/publication grant и current Agent API сохранит explicit Russian search-language support при LLM-ready one-call output. Сейчас первый пункт не доказан в этом исследовании, а Sonar уже помечен legacy, поэтому рекомендовать новую direct Sonar dependency в августе 2026 года было бы трудно защитить. citeturn31view0turn19search1turn19search8

**Появление RSS и прямых Telegram donor channels, скорее всего, уменьшит ценность “максимального российского индекса” и повысит ценность дешёвого corroboration search.** Это архитектурный вывод из вашего roadmap: когда primary content discovery приходит напрямую из donor sources, web backend чаще отвечает на вопрос «подтвердить, расширить, найти независимый источник», где Parallel/Tavily-style clean excerpts выгоднее голого Yandex/Google SERP. В таком состоянии системы primary OpenRouter+Parallel становится сильнее; Yandex остаётся специализированным Russian-recall oracle, а не обязательной зависимостью на каждом посте.

**Итоговое decision rule на 13 августа 2026 года:** запускать **OpenRouter `web` → Parallel Advanced** как primary, не использовать автоматический `:online` routing, оставить **Tavily Advanced** как fallback, а перед окончательной миграцией прогнать собственный Russian-source A/B против **Yandex native/SerpAPI-Yandex** и получить письменное подтверждение Parallel по downstream commercial publication. Это решение изменится не от ещё одного English benchmark, а от одного из двух видов нового evidence: **существенного преимущества Yandex/Tavily на вашей русской выборке или contractual ответа, меняющего право на создание и публикацию производного поста**.
