# Телеграм-конвейер: план реализации

Цель: довести Content Factory до состояния, когда Telegram-канал наполняется
регулярно — вручную, по расписанию и автоматически из источников, с генерацией
текста и картинок на двух языках, и когда видно, как работает сам конвейер.

Задачи ведутся в Beads под эпиком `content-factory-next-ja3`. Этот документ —
их обоснование и порядок; статусы смотрите в Beads, не здесь.

## Что уже работает

Проверено на живом канале `@content_zavod_adt` (этап `ja3.1`, закрыт):

| Путь                                    | Подтверждение                                |
| --------------------------------------- | -------------------------------------------- |
| Подключение канала через `/connect`     | канал в списке, `internalId` = username      |
| Текст с HTML-разметкой                  | сообщение 4                                  |
| Картинка из локального хранилища        | сообщение 5                                  |
| Комментарий тредом                      | сообщение 6                                  |
| Отложенная публикация через Temporal    | сообщение 7, `state=PUBLISHED`, точно в срок |
| Подписчики канала в разделе «Аналитика» | `getChatMemberCount`                         |

Бот `@content_factory_adtbot` настроен через Bot API целиком: аватар из
фирменного знака, имя, описания и команды на двух языках, права по умолчанию
при назначении администратором.

## Границы, установленные при разборе

Их не нужно перепроверять — они проверены обращениями к API и чтением кода.

- **Просмотров и репостов по посту в Bot API нет.** `getMessageStats`,
  `getMessagesViews`, `getChatStatistics`, `getMessageViews` — все `404`. Эти
  данные живут в MTProto, который требует сессию живого пользователя. Владелец
  продукта исключил такие методы. Считать закрытым вопросом.
- **Истории подписчиков в API нет.** `getChatMemberCount` отдаёт только текущее
  значение. Поэтому Content Factory сохраняет собственный ежедневный снимок и
  строит тренд по нему.
- **Реакции доступны официально** и приходят обновлением
  `message_reaction_count`. Единственный арендованный читатель `getUpdates`
  обслуживает и реакции, и подключение канала; отдельного опросчика у
  рукопожатия больше нет.
- **Импорт истории канала невозможен.** Флаг тарифа `import_from_channels` есть,
  но ни один провайдер его не реализует, и Bot API не умеет читать историю.
- **Модели настраиваются для организации.** Текстовая и графическая модели,
  провайдер и совместимый `baseURL` берутся из защищённых настроек; секреты не
  возвращаются в интерфейс после сохранения.
- **Большая часть площадочной аналитики считается на лету.** Для метрик без
  истории API добавлена общая таблица дневных снимков и отдельное версионное
  расписание Temporal; первым её использует число подписчиков Telegram.

## Два языка как основа продукта

Английский и русский равноправны — и в интерфейсе, и в содержании. Остальные
12 локалей остаются в репозитории, но активно не ведутся.

**Интерфейс.** Переключатель подключён к общему макету. Английский и русский
наборы имеют одинаковые ключи; регрессионный тест запрещает буквальные строки
в уведомлениях и заголовках открываемых модальных окон.

**Сервер всегда отдаёт английский.** `i18next.ts` использует
`i18next-browser-languagedetector`, который умеет только `document.cookie` и
`navigator.languages`. На сервере нет ни того, ни другого, поэтому SSR
отрисовывает язык по умолчанию, а браузер — язык из куки, и React сообщает о
расхождении. `proxy.ts:29` уже кладёт язык в заголовок
`x-i18next-current-language`, но никто его не читает. Осложнение: серверный
`i18next` — модульный синглтон, общий для всех запросов, поэтому
`changeLanguage` на нём протечёт между посетителями.

**Язык содержания явный.** Generator, copilot, chat и autopost передают `en` или
`ru` в промпт. Категории и темы имеют русские варианты, а канал хранит язык по
умолчанию отдельно от языка интерфейса.

## Порядок работ

Волны идут по зависимостям, внутри волны задачи независимы.

**Волна 1 — язык и честность интерфейса.** `ja3.12` серверный язык, `ja3.8`
оба языка на всех поверхностях, `ja3.14` объяснить пустое окно статистики,
`ja3.11` ссылки приватных каналов, `ja3.13` отказ от `text-white`.

**Волна 2 — измеримость.** `ja3.17` производственная аналитика из локальных
данных, `ja3.16` снимки подписчиков.

**Волна 3 — ИИ.** `ja3.2` ключ OpenAI и проверка генерации, затем `ja3.3` длина
автопоста и `ja3.4` язык содержания, затем `ja3.9` хранение выбранного языка.

**Волна 4 — источники и агент.** `ja3.5` RSS и каналы-доноры через мост,
`ja3.6` агент-генератор с поиском. Для каждого автоматического источника можно
отдельно включить веб-обогащение перед переписыванием. По умолчанию оно
выключено и не запускается при дословной перепубликации. Найденные источники
сохраняются с черновиком; недоступный поиск не останавливает обычную обработку
ленты. В интерфейсе явно отмечено, что включение увеличивает стоимость поиска.

**Волна 5 — вовлечённость.** `ja3.15` постоянный читатель обновлений и реакции,
затем `ja3.18` комментарии через привязанную группу обсуждений.

`ja3.10` (две неподключённые локали) не зависит ни от чего и делается когда
угодно.

## Производственная аналитика

`ja3.17` стоит объяснить отдельно, потому что это не заимствование из Postiz.

Модель `Post` уже хранит всё нужное:
`state`, `createdAt` против `publishDate` против `updatedAt`, `error` и связь
`errors`, `tags`, `image`, `content`, и главное — `creationMethod` со
значениями `UNKNOWN | WEB | MCP | API | AUTOPOST | CLI`, то есть чем именно
сделан пост.

Раздел «Аналитика → Производство» показывает за 7, 30 или 90 дней объём
публикаций, долю сбоев и их причины, среднее время от создания до публикации и
разбивку по происхождению. Период можно ограничить одним каналом. В расчёт идут
только верхнеуровневые `PUBLISHED` и `ERROR` с `publishDate` внутри выбранного
UTC-интервала; доля ошибок считается от суммы этих двух состояний, а время — по
`publishDate - createdAt` для опубликованных материалов. Считать по `updatedAt`
нельзя: это поле `@updatedAt`, оно сдвигается при любой правке, поэтому
исправление опубликованного поста через неделю выдавало бы неделю за время
подготовки. `publishDate` — это назначенный слот, а не момент фактической
отправки, поэтому пост, запланированный на месяц вперёд, отчитается месяцем;
зато показатель устойчив и объясним. Запрос всегда ограничен текущей
организацией.

Расчёт читает только локальную PostgreSQL через Prisma. Ни одного обращения к
площадке, поэтому он работает одинаково для всех каналов, включая те, у которых
аудиторных метрик нет вовсе. Теги и наличие медиа остаются доступными для
следующего расширения карточки, но не входят в текущий набор показателей.

Это та же идея, что несла производственная карточка прежнего Content Factory:
мерить завод, а не аудиторию.

## Единая очередь обновлений Telegram

Backend запускает ровно одного логического читателя `getUpdates` для общего
бота. Между несколькими экземплярами процесса лидер выбирается через короткую
аренду в PostgreSQL; аренда берётся перед ограниченным долгим опросом и
перепроверяется сразу после него, до применения батча. Долгий опрос длится до
20 секунд и вместе с обработкой может пережить аренду, а применить батч, уже
потеряв лидерство, значило бы посчитать каждую реакцию и каждый комментарий
дважды. Внешний webhook для этого не нужен.

Один поток принимает все нужные типы событий: команды `/connect`, публикации,
`message_reaction_count` и сообщения связанной группы обсуждений. Endpoint
подключения больше не обращается к Telegram сам: он забирает уже сохранённую
команду `/connect` из БД. Поэтому подключение канала и сбор вовлечённости не
могут украсть события друг у друга.

Заявка на подключение живёт 15 минут, а не весь срок хранения квитанции. Слово
подключения не привязано к организации, поэтому недельное окно означало бы, что
совпавшее или угаданное слово отдаёт чужой канал; за 15 минут человек либо
завершает подключение, либо начинает заново. Запрос без слова отклоняется
валидацией: раньше отсутствующий параметр снимал фильтр Prisma и выдавал самую
старую незавершённую заявку любой организации.

Каждый `update_id` записывается в той же транзакции, что и изменение метрики;
повторное событие ничего не меняет. Дубликатом считается только нарушение
уникальности самой квитанции: та же ошибка от строки метрики или обсуждения —
настоящий сбой, и принимать её за повтор значило бы потерять обновление.
Обновление, которое не удалось применить трижды, списывается — квитанция
пишется без применения действий, и курсор идёт дальше. Иначе одно неприменимое
событие держало бы курсор, а значит и все следующие события, бесконечно.
Квитанции хранятся семь дней — дольше
24-часового срока хранения обновлений Telegram — и затем удаляются. Реакции
сохраняются абсолютным числом по паре «канал + сообщение». Автоматическая
пересылка публикации в discussion group создаёт связь с исходным сообщением;
каждый прямой или вложенный ответ наследует эту связь и увеличивает число
комментариев.

Просмотры и пересылки по-прежнему не имитируются: Bot API их не выдаёт.
Удаление комментария Telegram отдельным обновлением не сообщает, поэтому
счётчик отражает полученные ответы, а не текущий размер очищенной вручную ветки.

## Ежедневные снимки подписчиков

Провайдеры могут явно поддержать `analyticsSnapshot()`. Ежедневное расписание
Temporal `integration-analytics-snapshots-v1` в 00:15 UTC запускает новый
однократный workflow `integrationAnalyticsSnapshotWorkflowV1`; существующие
workflow и activity не менялись. Пересечения запусков пропускаются, а
пропущенный запуск догоняется только в пределах 12 часов.

Activity обходит только активные подключения и сохраняет значения по ключу
«подключение + метрика + день UTC». Повторный запуск обновляет ту же строку, а
ошибка одного канала не останавливает остальные. При чтении сохранённые дни
объединяются с текущим значением API, после чего процент считается между первой
и последней точкой выбранного диапазона.

## Что должно остаться неизменным

- Контракты Temporal-воркфлоу и активностей не переписываются; при
  необходимости добавляется версионный преемник, а вызывающие переводятся.
- Поведение провайдеров не выносится за пределы их реализаций.
- Атрибуция AGPL и upstream, имена переменных окружения, таблиц и провайдеров
  сохраняются. Import namespace позднее отдельно мигрирован на
  `@contentfactory/*` задачей `content-factory-next-wcx.1`.
- `scripts/branding/brand-scan.cjs` остаётся зелёным.
- Никаких подключений реальных аккаунтов, публикаций, платных вызовов и пушей
  без явного разрешения владельца.
