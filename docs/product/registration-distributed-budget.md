# Распределённые ограничения регистрации

`POST /auth/register` использует существующий общий Redis для двух независимых
ограничений. Обычный отказ формы до записи аккаунта позволяет сразу исправить
форму. Он по-прежнему считается попыткой в защите от массовых запросов.

## Попытки и действия

| Ограничение | Что считается | Когда освобождается |
| --- | --- | --- |
| 10 попыток | Каждый запрос, в том числе ошибка DTO и безопасный отказ формы | Существующее минутное окно guard |
| 1 действие | Допущенная после проверки DTO попытка создать аккаунт или отправить письмо | Через 60 секунд либо после подтверждённого безопасного отказа |

Отказами до действия остаются только экземпляры `RegistrationFormRefusal` с
существующими кодами `email_plus_not_allowed`, `email_already_exists` и
`invite_email_mismatch`. Неизвестная ошибка, совпадающий текст, произвольный
HTTP 400, ошибка провайдера, запись аккаунта с последующей ошибкой письма и
успешная регистрация сохраняют резервирование. Никакой повтор запроса не
запускается автоматически.

Счётчик десяти попыток использует прежний `ThrottlerStorageRedisService`,
порог, TTL и блокировку. Меняется только идентификатор для регистрации: он
совпадает у реплик с одинаковым `JWT_SECRET` и после перезапуска backend.
При смене минутной группы HMAC применяется новый идентификатор, как и раньше.
Это сохраняет прежнюю границу минутного окна, включая возможность отправить
запросы по обе стороны этой границы; новый скользящий лимит десяти запросов
за любые 60 секунд не вводится. Login, forgot, resend, growth и остальные
маршруты сохраняют прежние идентификаторы и поведение.

## Атомарное резервирование

Две минутные HMAC группы — текущая и предыдущая — служат псевдонимами одного
случайного владельца. Lua проверяет оба ключа и записывает оба псевдонима за
одну атомарную операцию. У каждого ключа TTL ровно 60 000 мс; отказ по лимиту
не продлевает срок. Так учитывается и обычная смена минуты, и обратный порядок
доставки, когда запрос предыдущей минуты приходит в Redis позднее нового.
[Redis гарантирует атомарное выполнение Lua.](https://redis.io/docs/latest/develop/programmability/eval-intro/)

Освобождение сравнивает токен владельца отдельно на каждом псевдониме и удаляет
только совпавшие ключи. Поздний отказ старой попытки после истечения TTL не
может освободить резервирование новой. Ответ формы ждёт завершения освобождения;
сбой или таймаут освобождения возвращает `false`, а не подтверждение успеха.
[Сравнение владельца — стандартный способ безопасного удаления в Redis.](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)

## Доступность и предел ресурсов

Отсутствующий `JWT_SECRET`, `MockRedis`, неготовое соединение, ошибка Redis,
неизвестный ответ, таймаут или исчерпанный предел соединений закрывают допуск.
Регистрация получает HTTP 503 с кодом `registration_budget_unavailable` до
работы с аккаунтом и письмом. Для исчерпанного лимита действий остаются HTTP
429 и `Retry-After`, рассчитанный по оставшемуся Redis TTL.

Каждая операция с резервированием создаёт короткое соединение через
`ioRedis.duplicate`, использующее тот же сервер, базу и существующие настройки
доступа. Очередь до готовности, повтор неподтверждённых команд и переподключения
на этом соединении отключены. Общий клиент и его настройки сохраняются.
Дедлайн соединения и Lua вместе — 1000 мс, одновременно допускается не более
16 таких операций на процесс. При любом выходе соединение отключается и
занятое место возвращается. Отменённое подключение не может позже отправить
Lua. Уже отправленная команда с потерянным ответом может оставить ключ до TTL;
она не повторяется и не разрешает действие без подтверждения.
[ioredis описывает очереди и повтор неподтверждённых команд.](https://raw.githubusercontent.com/redis/ioredis/v5.10.0/README.md)

Для guard регистрации ожидание также ограничено 1000 мс. Уже переданный его
существующему общему хранилищу счётчик может завершиться позднее отказа и
засчитать попытку. Контроллер после такого отказа не запускается; счётчик не
возвращается и новая попытка автоматически не выполняется. Одновременно
допускается не более 16 ещё не завершённых проверок guard на процесс. Таймаут
HTTP ответа не освобождает это место: оно возвращается только после фактического
успеха либо ошибки исходной проверки. При заполнении новых обращений к Redis
и контроллеру нет. Это ограничивает и очередь старого общего клиента.

## Приватность и границы

Адрес нормализуется только в памяти запроса с прежним порядком proxy заголовков.
От существующего `JWT_SECRET` выводится отдельный HMAC ключ для каждого из двух
ограничений. Для резервирования Redis получает минутные непрозрачные
идентификаторы длиной 128 бит и случайный 128-битный токен владельца; guard
сохраняет штатный хэш ключа и счётчик попыток. IP, email, приглашение,
cookie и user-agent в ключи, значения и сообщения об этих ограничениях не
попадают. Новая долгоживущая идентичность или новый секрет не добавляются.

Реплики должны использовать один Redis, одинаковый существующий `JWT_SECRET`
и согласованные часы. Перезапуск backend сохраняет ограничения; утрата данных
самого Redis или смена ключа доступа к JWT относятся к отдельным эксплуатационным
границам. Резервирование ограничивает допуск на 60 секунд и не заменяет
уникальность аккаунта или транзакции базы данных.

## Проверка

`tests/registration.distributed-budget.test.cjs` содержит отдельные тесты на
реальном одноразовом Redis: несколько лимитеров, гонка запросов, новый экземпляр,
оба порядка смены минуты, полный неизменённый TTL 60 секунд, позднее освобождение,
очистка соединений и общий счётчик guard. Там же проверяется цепочка ошибок DTO
и всех трёх отказов формы через два контроллера с реальным Redis.

Реальные тесты включаются только с `CF_REGISTRATION_TEST_REDIS_URL`, указывающим
на принадлежащий проверке Redis на loopback. Без него реальные случаи явно
пропускаются; заглушка для unit-тестов не считается распределённым доказательством.
