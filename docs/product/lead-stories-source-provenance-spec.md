# Сюжеты поводов и происхождение источников — предложение

Статус: принято root для реализации `content-factory-next-0qgn`;
критерии Beads сохраняются, production-приёмка принадлежит root. Дата: 01.10.2026.

Область: `75xn.33` и `75xn.34`. Решение владельца от 01.10 сохранено:
разные статьи об одном конкретном событии объединяются в одну карточку со всеми
ссылками; неподтверждённая перепечатка остаётся видимой с пометкой; заявленный
первоисточник не повышается до подтверждённого без проверяемого доказательства.

## Наблюдаемая исходная граница

`LeadTopicGateway` сейчас отбрасывает дубликаты только по каноническому URL и
возвращает по одной записи на URL. Кандидат несёт один `sourceUrl`; проверка
страницы ограничена восемью чтениями, которые уже используются для даты.
`ContentLeadService` передаёт дальше только одну ссылку, `ContentLead` хранит
тоже один `sourceUrl`, а `ContentLeadRepository.listLeads` возвращает поля этой
записи. Адаптер UI разбирает одну ссылку; карточка `LeadCardView` её не
показывает. Значит, одного изменения сортировки в шлюзе недостаточно: список
ссылок должен пройти весь путь до сохранённой карточки.

Опорные текущие файлы:

- `libraries/nestjs-libraries/src/content-intelligence/leads/lead-topic.gateway.ts`
- `libraries/nestjs-libraries/src/content-intelligence/leads/lead-feed.gateway.ts`
- `libraries/nestjs-libraries/src/content-intelligence/leads/community-topic-discovery.service.ts`
- `libraries/nestjs-libraries/src/content-intelligence/leads/content-lead.service.ts`
- `libraries/nestjs-libraries/src/content-intelligence/leads/content-lead.repository.ts`
- `libraries/nestjs-libraries/src/database/prisma/schema.prisma`, модель `ContentLead`
- `apps/frontend/src/components/content-intelligence/content-leads.adapter.ts`
- `apps/frontend/src/components/content-intelligence/content-leads.tab.tsx`, `LeadCardView`

Оставить неизменными существующие окна свежести, фильтрацию мусора, кэш и
платный путь, правила RSS-источников и входы Temporal workflow/activity.
`ContentLeadCheckWorkflowInput` и `ContentLeadCheckActivityInput` не получают
новых полей. `fn33.132` остаётся отдельным критерием: язык результата сам по
себе не доказывает предметную релевантность.

## Видимое поведение

1. В одной проверке TOPIC две записи становятся одной карточкой лишь при
   достаточном свидетельстве одного события. Похожие темы, общий бренд или
   близкая дата сами по себе не объединяют записи.
2. Карточка показывает все различные найденные URL. Для каждого URL сохраняется адрес и статус первичности.
   Заголовок, дата и короткая выдержка сохраняются у представителя карточки. Повтор того же канонического URL не создаёт второй видимой
   ссылки.
3. Явная ссылка «источник» с исходной страницы сохраняется как отдельная
   атрибуция: чей материал на неё ссылается, целевой URL, перечислимый статус заявления. Пока подтверждения нет, UI говорит об этом словами, а не
   только цветом или положением.
4. Статус `VERIFIED_PRIMARY` допустим только при наличии сохранённого прямого
   свидетельства, относящегося к первичному материалу. Утверждение страницы,
   доменное имя, наличие ссылки или появление URL в той же поисковой выдаче по
   отдельности этого статуса не дают. Связь «ссылка найдена в этой проверке» и
   роль «подтверждённый первоисточник» — разные состояния.
5. Если в группе есть подтверждённый первоисточник, он становится первой
   ссылкой карточки и источником её основной ссылки. Если такого доказательства
   нет, остаётся детерминированный представитель найденных статей; заявленная
   перепечатка видна с пометкой, и все остальные ссылки остаются доступны.
   Существующие правила свежести не ослабляются.

## Детерминированное объединение

Применять после существующей фильтрации по URL, релевантности, дате и окну
свежести; агрегатор нельзя спасать от старого/недатированного фильтра одной лишь
ссылкой на первоисточник. Область объединения — один проход одной TOPIC
подписки, в том числе при выборе существующего paid или community режима. Для
community-кандидатов входной порядок групп сохраняет порядок исходных кандидатов;
отдельное ранжирование и его видимость после persistence относятся к `75xn.9` и
этой задачей не принимаются. RSS и разные подписки друг с другом не объединяются.

Первый ограниченный критерий повторяет предложенный в `75xn.33` сигнал, но
делает его симметричным: у каждой пары должны быть известны даты с разницей не
более двух UTC-календарных дней и не менее трёх общих уникальных стемов из
заголовка и очищенной выдержки. Стемы предмета подписки вычитаются. Используется
существующий `textStems` из `lead-junk.ts` (нижний регистр, первые пять букв или
цифр); это эвристика, не обещание семантической эквивалентности.

Алгоритм complete-link: отсортировать кандидатов по UTC-дате, нормализованному
заголовку и каноническому URL; добавить кандидата в группу, только если он
проходит критерий с каждым её элементом. Не строить транзитивные компоненты по
цепочке совпадений. Если кандидат подходит сразу нескольким группам или
свидетельство неполное/неоднозначное, оставить его отдельной карточкой и
сохранить диагностическую причину. Результат не зависит от порядка, в котором
провайдер вернул массив. При недостатке данных предпочесть пропущенное
объединение ложному.

Представитель группы выбирается детерминированно: сначала сохранённое
`VERIFIED_PRIMARY`; внутри одного класса — самая поздняя допустимая дата, затем
канонический URL по возрастанию. Все кандидаты группы всё равно остаются в
списке источников. В первой версии не выполнять глобальный fuzzy-merge старых
строк и не менять сохранённые решения человека.

## Происхождение и граница чтения страниц

Для атрибуции читать только явные source/original-ссылки из HTML, уже полученного
тем же ограниченным `readPage` при датировке. Не добавлять fetch/redirect/follow
к чужому URL. Оставить существующие robots, SSRF/network-policy, deadline и
лимит `MAXIMUM_PAGE_READS = 8`; недоступная или нечитанная страница означает
«неизвестно», а не «ссылки нет».

Персистировать URL и малую текстовую выдержку, а не HTML, полную страницу,
секреты или произвольный payload. Целевой URL цитаты может храниться как
непроверенное утверждение, даже когда его нельзя нормализовать; такой адрес не
открывать и не продвигать. Канонизацию обычных URL делать существующим
`canonicalizeSourceUrl` и сохранять исходное написание рядом, чтобы отображение
не теряло исходную ссылку.

Архив `.codex/stages/content-factory-next-75xn/evidence/quality-2026-09-13-after/`
содержит три указанные владельцем положительные пары (`FINDINGS.md`) и записи
CryptoRank с заметками о ссылках на Incrypted (`outB/leads-dated.json#/leads/1`)
и Forkast (`#/leads/8`). В этих JSON есть заметка проверяющего, но нет снимка
HTML и независимого доказательства первичности целевой публикации. Для реализации
эти две атрибуции поэтому остаются `CLAIMED_UNVERIFIED`; заметка не даёт права
автоматически поставить `VERIFIED_PRIMARY`.

Негативная пара того же архива: `outB/leads-dated.json#/leads/0` и
`#/leads/9` — разные описанные события AI Act с датами 04.09 и 03.09.2026.
Она проверяет, что общий предмет и близкие даты не заменяют три общих стема.
Реальные fixture-векторы следует минимизировать до нужных полей и хранить с
путём/pointer исходного evidence; не копировать полные ответы или тексты страниц.

## Хранение и совместимость

Оставить `ContentLead.sourceUrl` как совместимое поле основной ссылки. Добавить
одно nullable, версионированное JSON-поле `ContentLead.sourceRefsJson` для списка
найденных URL и атрибуций. Конверт `version: 1` имеет строго проверяемые
массивы `sources` (до 50 записей) и `attributions` (до 50 записей), флаг
`truncated` и только URL-поля плюс перечислимое состояние: `sources` хранит
`url`, nullable `canonicalUrl` и `primaryStatus`; `attributions` — `fromUrl`, `targetUrl`
и `state`. URL длиннее 2 048 знаков, неизвестные ключи/статусы, массивы сверх
лимита и любые foreign tenant/entity IDs запрещаются. В полях не хранить HTML,
произвольные payload, заголовки, выдержки, даты, провайдеров или другую запись.
Если объединение найденных URL превышает cap, отказать запись и сохранить
предыдущие данные транзакционно. При ограничении атрибуций установить
`truncated: true` и явно сообщить об ограничении в карточке. Невалидный
JSON на чтении означает безопасный fallback на `sourceUrl`; на записи — отказ от
некорректной структуры.

`sourceUrl`/`url` обычного найденного материала проходят существующий
`canonicalizeSourceUrl`; рядом сохраняется исходное написание в `url`. Заявленный URL
хранится как непроверенное текстовое утверждение, не открывается и не
нормализуется для сетевого доступа. В `sourceRefsJson` нет foreign tenant/entity
IDs. Если будущий тип доказательства введёт `evidenceId`, перед чтением или
записью требуется отдельная проверка `organizationId` у этой сущности.

Обычный feed-путь остаётся без story-clustering и использует существующий
`sourceUrl`; frontend fallback оставляет эту ссылку доступной. Для TOPIC
repository выполняет сохранение lead и одного проверенного `sourceRefsJson` JSON
атомарно. Если один
новый кластер содержит URL ровно одной существующей записи этой же организации и
подписки, использовать её `id`/`externalId`, объединить source refs по
каноническому URL и обновить только допустимое представление карточки; не трогать `status`,
`acceptedAt`, `dismissedAt` и авторов решения. При совпадении с несколькими
старыми строками не сливать их автоматически: вернуть безопасный конфликт,
сохранить исходные решения и оставить ручное разрешение отдельно.

Новая группа получает версионированный stable key из отсортированных
канонических URL. Последующие проверки с хотя бы одним уже сохранённым URL
разрешаются к той же записи через URL из JSON-конверта. Смена всего набора URL
без общего адреса не позволяет надёжно доказать историческую идентичность; в
этой версии не угадывать соответствие по похожему заголовку.

API списка сейчас возвращает результат `ContentLeadService` без отдельного
DTO-преобразования. Репозиторий должен включить связанные ссылки в этот ответ;
адаптер frontend разбирает их с безопасным fallback на старое `sourceUrl` для
исторических строк без нового JSON-конверта. `LeadCardView` показывает все
ссылки и понятную подпись неподтверждённой атрибуции. Использовать обычную
семантическую внешнюю ссылку и текущие токены/переводы; новый UI-примитив не
нужен. Добавлять строку в component inventory только если реализация всё же
создаст переиспользуемый компонент.

## Миграция и границы доказательства

Нужна additive-only схема: одной колонки `sourceUrl` недостаточно для двух и
более URL и связи «кто заявил этот источник». Одну nullable JSON-колонку
вывести из текущей Prisma-схемы через принятый
`prisma migrate diff`, отбирать отдельный SQL и пропускать через
`validate-prisma-migration-sql.cjs`. Проверять его на одноразовой PostgreSQL:
пустой новый diff после применения; запросы `listLeads` сохраняют tenant-фильтр;
повторная запись не дублирует URL; статусы принятой/отклонённой записи не
меняются. JSON не хранит foreign tenant/entity IDs. `prisma db push` к production
запрещён.

Инженерное доказательство — тесты кластеризации/парсера, путь
candidate→repository→API→карточка, миграционный guard и disposable-DB проверка.
Оно не заменяет root-owned проверку реальных положительных/отрицательных
примеров и сохранённого source evidence. Публичный архив с заметкой об
атрибуции не считается подтверждением первоисточника; отсутствие evidence —
«неизвестно», а не «подтверждено».

## Уточнения принятой реализации 01.10.2026

- Root подтвердил abstention для архивной пары `/leads/11` и `/leads/12`:
  разные языки, проверенные даты 30.08 и 26.08. Без общего прямого evidence
  эта пара не обязательный положительный пример и не объединяется.
  Пары `/leads/4` + `/leads/5` и `/leads/13` + `/leads/14` проходят.
- Дополнительный консервативный барьер требует два общих стема заголовков
  вне темы. Одинаковая шаблонная выдержка разных статей не доказывает событие.
- Поле называется `sourceRefsJson`; хранится только строгий URL-only конверт.
  Заголовок, выдержка и дата остаются полями представителя карточки;
  отдельные копии текстов всех статей в JSON не сохраняются.
- Найденные URL при повторной проверке не обрезаются. Если объединение
  превысит 50 URL, запись отказывает и транзакция сохраняет предыдущие данные.
  Только ограниченные attribution evidence могут иметь `truncated: true`.
- Автоматический парсер никогда не создаёт `VERIFIED_PRIMARY`. Сохранённая
  ссылка, домен и заметка архивного проверяющего остаются неподтверждёнными.
- Сохранение работает в Serializable-транзакции с максимум двумя повторами
  `P2034`; пересечение нескольких старых строк — безопасный конфликт.
- Disposable DB/schema release proof и итоговую проверку исполняет root.

## Уточнение после проверки root

Точный маршрут `cryptorank.io/news/feed/` (также `www.cryptorank.io/news/feed/`)
признан маршрутом перепечаток по двум сохранённым материалам `/leads/1` и
`/leads/8`. Карточка сообщает «Перепечатка · первоисточник не подтверждён»
даже без прочитанного HTML и на старом fallback `sourceUrl`. Это узкое правило
не распространяется на другие пути CryptoRank, поддомены или похожие имена.
Оно не определяет первичный URL, не создаёт доказательства первичности,
не меняет статус атрибуции и не добавляет fetch или поле JSON.

Транзакция сопоставления читает историю подписки один раз на попытку и только
`id`, `externalId`, `sourceUrl`, `sourceRefsJson`. Внутри этой же попытки снимок
дополняется созданными строками и обновлёнными наборами URL. История не
обрезается лимитом: иначе старые URL могут исчезнуть из проверки пересечения.
Serializable-повтор создаёт новый снимок; решения пользователя не обновляются.
